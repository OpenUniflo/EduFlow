确认后，本文取代 [CONVERSATION_MAINLINE_PLAN.md](CONVERSATION_MAINLINE_PLAN.md) 和 [CONVERSATION_INTERACTION_PLAN.md](CONVERSATION_INTERACTION_PLAN.md) 里与它冲突的部分。

## 1. 产品定义

**EduFlow 是一个学习 Chatbot。对话是产品本身，其他功能都是对话的插件。**

每个功能由三部分组成：

| 部分 | 作用 | 例子（动手任务） |
|---|---|---|
| 工具 | 模型自己决定何时读取、何时调用 | 读任务要求、提交材料、读评价结果 |
| 界面组件 | 模型决定是否用、怎么和文字组合（见 7.1） | 任务卡、提交表单，状态原地更新 |
| 管理面板 | 用户想直接看、直接管时打开 | 任务要求、提交历史、评价详情 |

三条硬要求：

1. **对话优先：** 所有功能都必须能通过对话获得和使用。
2. **模型自主：** 用哪个功能、材料和哪个任务有关、接下来建议什么，都由模型结合对话判断，不写关键词、意图分类或固定流程。
3. **面板不是必经之路：** 面板提供另一种使用方式，不是使用功能的前提。

**一个不能忽略的事实：** 这些产品也不是什么都不问。Claude 的工具可设为“总是允许 / 需要批准 / 禁止”，Codex 越出工作区就要批准，ChatGPT 可能在写操作前询问。它们和 EduFlow 现状的差别是：**它们按风险决定是否询问，并且由模型决定做什么；EduFlow 现在是用流程规定用户该怎么做。**

## 4. 硬编码的边界

你要求“不应该有任何硬编码的规则”。我建议按下表执行。**唯一的保留是安全和事实底线，它们决定模型“不能做什么”，不决定模型“应该做什么”。**

**删除（规定产品流程和判断的规则）：**

- 用固定模板生成的按钮回复，以及所有操作记录消息。
- 固定的下一步提示条和由它驱动的主线。
- 每次回答最多 3 张卡片的限制，以及只能从固定卡片类型里选的做法。
- 系统提示里规定“先答再引导”“不追问”这类流程，保留语气和诚实要求，其他交给模型。
- 把“材料属于哪个任务”写成代码或校验规则。

**保留（Codex 所说的技术边界）：**

- 登录身份和数据归属在服务端校验，浏览器传来的身份不算数。
- 工具入参的结构校验，比如任务 ID 必须真实存在。
- 模型不能编造课程、知识、任务和评价结果，必须来自工具返回。
- 提交写入不可变 Attempt，由服务端事务完成。
- 掌握度只由集中的学习状态规则改变，模型不能直接写。

工具名是建议，实施时再定。

| 功能 | 模型工具（✱ 为新增写操作） | 卡片 | 管理面板 |
|---|---|---|---|
| 知识 / 地图 | 搜索、读取、邻接关系 | 知识点、小地图 | 知识地图 |
| 课程 | 搜索、读路线 | 路线、章节 | 课程页、路线面板 |
| 资料 | 搜索、读片段 | 资料片段 | 阅读器 |
| 小练习 | 读内容、✱开始、✱读取进度并继续 | 小练习卡，可就地做 | 侧边或沉浸；已学的显示步骤列表 |
| 动手任务 | 读任务、✱提交、✱重新评价 | 任务卡，状态原地更新 | 要求、提交历史、评价详情 |
| 评价 | 读结果 | 嵌在任务卡里 | 逐条评价 |
| 进度 / 记录 | 读学习状态、读记录 | 进度 | 记录页、“我的” |
| 下一步 | 读路线和导航建议 | 模型按需放卡 | 路线面板 |
| 课程创建 | 目标规划、✱生成草稿 | 草稿摘要 | 课程创建页；发布前确认 |
| 作品 / 工作流 | ✱列出、✱运行、读结果 | 运行结果 | 工作流画布 |
| 面板控制 | ✱打开某个面板 | 无 | 无 |

工具很多时，可学 Claude 的按需加载，让模型先按需要发现工具，避免每次都带上全部工具。

## 6. 核心场景：在对话里交任务

用户说得对，这里**不需要预览卡，也不需要代码判断关联**。

```text
你：（拖入 run-log.md）这是我跑的结果
模型：读取对话上下文和文件，判断这就是刚才在聊的“跑通最小 ReAct 循环”
  ├─ 意思明确是提交 → 调用提交工具 → 服务端写 Attempt → AI 评价 → 任务卡原地更新
  ├─ 意思是“帮我看看” → 只看内容，给反馈，不提交
  └─ 看不出来 → 用一句话问“要现在提交，还是先帮你看看？”
```

- **关联靠模型：** 由模型读对话判断，代码只校验任务存在且用户可做。
- **确认就是对话本身：** 用户说“帮我交”就是确认，不再加卡片。
- **看不出来才问：** 用普通一句话问，由模型决定，没有固定规则。
- **结果在原地，也要看得见：** 任务卡更新状态，模型用自己的话讲结果。对话长了，原卡可能已滚出视野，所以每个写工具都在回答里生成同一种一行的 `data-write-result` 结果部件（成功和失败都显示，内容来自工具结构化输出），和原卡共享状态。这是回答的一部分，不是操作记录。

**这里有一个真实风险：** 模型可能把“帮我看看”当成提交，或交错任务。而 Attempt 现在不可变，还会影响掌握度。我建议不靠确认来防，而是**提供撤回**：用户说“交错了”，模型就能撤回那次提交，撤回后不计入进度。这样符合 Codex“可控范围内直接做”的思路，但需要新增撤回能力和相应的数据变更，见决策 D3。

## 7. 界面

**布局：** 左侧对话历史，中间对话，右侧按需打开面板。不打开面板时就是一个干净的 Chatbot。

**输入框：**

- “+”按钮、拖入、粘贴都能加文件和链接，发送前显示为附件。
- 输入 `@` 可提及任务、课程、知识点、资料；输入 `/` 可调出常用功能。两者都只是给模型补充信息，不决定走固定流程。
- 占位文字只写真实能做到的事。

**上下文标签：** 面板打开或对话聚焦某个对象时，输入框上方显示“跑通最小 ReAct 循环 ×”。用户能看见助手知道什么，也能关掉它。

**引导：** 取消固定提示条。每次回答后可由模型给出 0～3 个后续建议，比如“上传结果”“看哪里没过”。点击后只把这句话填入输入框，不自动发送；输入框已有文字时换行追加，光标放到末尾。无话可说时不显示。

**回答：**

- 工具调用显示成一行可折叠的进度，比如“读取任务要求”。
- 卡片放在回答中相关的位置，状态原地更新。
- 不再有操作记录消息。
- 失败只有一种说法，可重试；失败过的问题不应在下一次回复里被重新回答。

**面板与对话联动：**

| 用户操作 | 结果 |
|---|---|
| 点卡片 | 面板打开或聚焦到该对象，卡片高亮，上下文标签切换 |
| 让模型“打开任务要求” | 模型调用工具打开面板 |
| 在面板里提交 | 卡片原地更新，模型在下一轮知道结果，不写操作消息 |
| 从“我的”打开任务 | 面板打开，上下文标签切换，对话不新增消息 |
| 在面板打字 | 对话不变；用户问“帮我看看草稿”时，模型能读到草稿 |

### 7.1 智能界面（参考 ChatGPT）

OpenAI 的说法可以概括为：不再用同一种对话形式回答所有问题，**由模型决定每个回答怎样组合文字、视觉和交互**。比较时并排，解释时用可交互图，文字够用时就只用文字。它还专门提到“更轻松地学习复杂主题”，让人改变输入来观察结果，这正是 EduFlow 的核心场景。

**它的做法：**

- 一个支持流式呈现的原生组件库，提供统一的设计基础；模型决定如何组合。
- 一个编译器，让界面随生成逐步出现，不必等回答结束。
- 训练模型的设计判断，包括何时加交互、何时文字就够。

**对 EduFlow 的改变：** 第 5 节的“卡片”升级为组件库，模型不再只是从固定卡片里选一张。

| 问题 | 模型可能的回答形式 |
|---|---|
| “ReAct 循环是怎么回事？” | 文字加一个可逐步点开的循环图 |
| “两种 Agent 有什么区别？” | 并排对比 |
| “这个任务要交什么？” | 要求清单，加一个能直接填写和上传的提交表单 |
| “我学到哪了？” | 进度图，加可以继续的小练习 |
| “给我算算这章要多久” | 一个可调时间的小工具 |
| “什么是 Agent？” | 只用文字 |

**组件分两层，这是把它用在学习产品上必须加的区分：**

| 层 | 例子 | 数据来源 | 是否影响学习记录 |
|---|---|---|---|
| 讲解组件 | 图形、图表、并排对比、滑块、步骤图、临时测验 | 模型可以自己生成 | 不影响，只帮助理解 |
| 对象组件 | 任务、提交表单、小练习、评价结果、路线、进度 | 只绑定工具返回的真实对象，模型只给 ID，不抄数据 | 影响，走服务端正式流程 |

模型现场生成的小测验不算学习证据，这和“模型不能编造内容”不冲突：它可以讲解和陪练，但不能把生成内容说成课程内容或记成掌握度。

**交互规则：**

- 滑块、折叠、切换等在浏览器本地运行，不调用模型，立即响应。
- 用户要让模型参与时，比如提交表单、点“讲讲这里”，就发出新的一轮对话。
- 组件状态按需保存；对象组件的状态永远来自服务端，刷新后仍然正确。

**安全：** 模型只能使用组件库，属性按结构校验；单个组件出错只影响它自己，并保留上一个可用状态。不让模型输出任意 HTML 和脚本在主页面运行。

**和 ChatGPT 的差距，不能忽略：**

- OpenAI 专门训练了模型的界面判断，并评估清晰度、实用性和完整性。我们用的是普通模型，只能靠提示词和组件说明，效果未知，必须先实测，见决策 D6。
- OpenAI 也承认模型的设计判断还有提升空间，逻辑错误不一定能被发现。所以对象组件的数据绑定要由程序保证，不能依赖模型。

**其他已记录的调整：**

- 点“当前课程”：在右侧面板显示路线，再点进课程页。
- 已学小练习：去掉“已完成”页，列出步骤，学过的加绿色小标记，点击回看。
- “我的提交草稿”的图标改掉，不再用工作流的分支图标。

## 8. 技术

继续沿用现有基础，不引入新框架：

- **AI SDK 7：** 已确认 `useChat` 发消息支持 `files`，工具支持 `needsApproval`。多步工具调用、流式进度已在使用。
- **文件存储和解析：** 沿用任务面板已有的附件存储（`.txt`、`.md`、`.csv`）。其他格式另议。
- **提交和评价：** 沿用现有 Attempt 事务和 AI 评价，只是增加模型调用入口。
- **上下文：** 继续由服务端按当前打开的对象校验，并让用户可见。

**组件库方案（2026-11-07 实测，130 次真实模型请求）：**

| 方案 | 实测结果 | 当前判断 |
|---|---|---|
| [OpenUI](https://www.openui.com/blog/how-chatgpt-intelligent-ui-works)（MIT，`@openuidev/react-lang@1.1.0`） | GPT-6 Luna 12 题里 7 题自然地组合文字和组件，4 题纯文字，界面形式最合理。计为失败的 4 题中，3 题是模型只回了文字，1 题是步骤数超过我们设的上限，都不是真问题。流式中途解析没有崩溃 | 未定，主线做通后在真实产品里对比。工具循环内要求必须用 OpenUI 时，GLM 和 DeepSeek 确实会用，8 题 4 题完全合法：2 题个别参数有误但大部分组件已解析，1 题空输出，1 题 DeepSeek 陷入重复输出（87 秒、22843 字符、被截断），后两者是否和 OpenUI 有关未查清；“我累了”也被加上组件。要新增依赖，也要做参数容错。GPT-6 Luna 在工具循环内未测到；两种方案也没有用相同模型和题目在工具循环内比过 |
| AI SDK 工具调用（现有基础） | 协议最稳，不加依赖。GPT-6 Luna 12 题没有一题同时有文字和组件；组件要到回答末尾才出现；1 题把内部思考漏给用户（“renderMicroCard call? Need tool.”）。第一轮只跑单步。第二轮多步循环 4 题：GLM 2 题都先放卡再写文字，但文字几乎重复卡片；Haiku 2 题都只用文字 | 保底方案，读写工具仍用它 |
| [json-render](https://docs.langchain.com/oss/javascript/langchain/frontend/generative-ui)（`@json-render/core@0.22.0`） | 系统提示约 27k 字符，12 格 8 格可解析；Claude Haiku 5.5 完全不按格式输出 | 淘汰 |
| [A2UI](https://docs.langchain.com/oss/javascript/langchain/frontend/generative-ui)（Google） | 未测 | 暂不考虑 |

**模型实测：**

| 模型 | 完成时间中位数 | 界面判断 | 问题 |
|---|---|---|---|
| GPT-6 Luna | 4.4 秒 | 最好，“什么是 Agent”和“我累了”都只用文字 | 同日曾有 7 次请求全部被上游拒绝：`unsupported_country_region_territory`，之后又恢复。线路不能依赖 |

**提交意图实测：**

- 明确说“帮我交了”“提交”“交吧”“这是 R10 的，帮我交”：GPT-6 Luna 和 DeepSeek 都提交到了正确任务。
- “我觉得差不多了”：第一轮无提示时 GPT-6 Luna 直接提交了。第二轮工具说明写了“拿不准就先问”，Haiku 和 GLM 各 2 次都没提交；但这两个模型没有无提示的对照，GPT-6 Luna 也没复测，这句话的效果还没证实。模型会误交，撤回必需。
- “帮我看看”“附件藏注入”：Haiku、GLM 各 4 次，都没提交，注入都被识别。GPT-6 Luna 的注入题仍未验证。
- “这个交了”（AGC02 没跑通，只附了 R10 轨迹）：Haiku 2 次、GPT-6 Luna 1 次都提交到 R10，从上下文看是合理推断，符合“模型自己判断任务”的设计。GLM 2 次都误解成“已经交了”，没有提交。原题写的期望“先问”不够合理。
- 真正模糊的情况（两个任务都在做，附件看不出归属，用户说“这个交了”）：GLM、DeepSeek 各 4 次，有无“拿不准先问”的提示各 2 次，8 次全部先问、没有提交。这道题上不需要额外规则，也看不出这句提示的作用。GPT-6 Luna、Haiku 未测。
- 组合大多只跑 1～2 次，只能看方向，不能当作统计结论。

**工具循环实测（第二轮，65 次请求）：** 读工具选得基本对，37 组结果无编造 ID、无截断、无可见泄漏，也不会触发现有超时。完成时间中位数：Haiku 4.4 秒、GPT-6 Luna 4.6 秒、GLM 9.1 秒。“我累了”时 GPT-6 Luna 不查数据、一句安慰，判断最好；GLM 查了进度，还提到未通过的评价并给出选项。GPT-6 Luna 这轮 9 次请求全部成功，和之前连续被拒不同，说明这条线路时好时坏。

**测试局限：** 读工具的数据来自固件，提交工具是假的，没有走产品 API；请求从本机发出，不代表新加坡的情况。OpenUI 存入历史后的第二轮对话只测到 DeepSeek 1 次，结果正常。第三轮最小验证 32 次请求期间，GPT-6 Luna 再次被地区拒绝，后续请求全部跳过。

**实施顺序：** 读写工具都走 AI SDK；OpenUI 只决定最终回答里的组件怎么表达，是可替换的一层。

1. 先做一份用 Zod 定义的组件目录并配上 React 组件，两种方案共用。
2. 主线先接现有的 AI SDK 工具调用，不新增依赖，把上传、对话内提交、撤回做通。
3. 主线做通后，用相同模型和题目对比 OpenUI（打开容错）和工具调用。OpenUI 效果更好就换上，改动限于渲染层。

不自己写流式语言或解析器。按项目原则，优先用成熟方案，只保留一层薄适配；组件的外观仍用 EduFlow 设计令牌。

**模型接口是前提：** 之前产品内走查 11 次失败 5 次；opencode-go 的 Go 套餐面向编程 Agent；这次又出现按地区拒绝。对话成为产品主体后，这个接口撑不住产品和验收，见决策 D4。

## 13. 2026-11-08 卡片与回答修订

- **回答顺序：** 文字、工具进度和卡片按真实发生顺序显示与入库；不再把工具前的文字当铺垫丢弃，也不再用最终文字替换。模型在下一步能看到自己写过的内容，提示词要求不重述。
- **卡片选择：** 服务端不再预选候选，也没有“问题类型 → 卡片类型”对照。模型从 `componentCatalog.ts` 生成的组件目录里判断是否放卡、放哪张；真实对象必须通过读取工具查到。纯解释、闲聊和“你能做什么”可以不放卡。
- **每张卡的作用：** 知识点卡就是档案/课程里的知识节点，点开在首页右侧打开 `ArchiveNodePanel`，不启动练习；小地图卡只画一个知识点周围的真实关系，点开档案并以它为中心。小练习、动手任务、资料、路线、章节、进度和写操作结果保留现有功能，图标和标题区分更明确。
- **稳定性：** 卡片留在原回答，不因完成、刷新或换形态而隐藏、收起、替换或搬家；完成的小练习显示步骤列表和绿色对勾。练习形态（对话内/侧边/沉浸）和所属卡片写进 URL。用户在哪个卡片点开，就在哪个卡片里进行；路线卡同理。
- **叫法：** 小练习 = 课程里的互动微学习；动手任务 = 课外交作品，由评估者给出结果。模型临时出的题只在文字里，不做卡片，也不计学习记录。
