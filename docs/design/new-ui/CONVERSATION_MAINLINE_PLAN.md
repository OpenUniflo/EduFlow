# 对话主线：设计与实施计划

日期：2026-11-05 · 状态：阶段 0～4 本地验收通过，未提交、未部署；阶段 5 未开始 · 范围：桌面端学习者（≥ 1280 宽）

交互原型：[EduFlow 对话主线原型](https://claude.ai/artifact/5Dq9Rfz2iGQNzqtBRFQEo3)。流程和交互以原型为准；助手回复与 AI 评价在原型里是示意文案，不是定稿。

本文档记录设计、计划和各阶段的验收结果。第 8 节中阶段 1～4 的规则改动已写入 `docs/rules/`。

## 1. 为什么要改

2026-11-05 用全新账号走查，发现三类问题：

- **没有主线：** 新用户的第一句话就失败，后面「开始学习」「回到首页看变化」也是断的。
- **门槛太高：** 进入课程首先看到 31 张卡片的 3D 课程树，还要理解知识节点、能力模型、匹配度等概念。
- **能力没接上：** 目标规划本身可用（直接调用接口能匹配到覆盖 83% 目标的课程），但首页对话调用不到它。

## 2. 设计原则

1. **从对话开始，不限定第一句话。** 所有用户都从首页进入，不需要先选课程。第一句话可以是提问、闲聊或还没想清楚的想法，不假设它是学习目标。
2. **由简单到复杂。** 用户不需要先理解产品，复杂功能等用得上时才出现。
3. **几分钟内能完成的留在首页，** 需要长时间专注的才跳转，完成后回到对话。
4. **对话是主场，但不靠打字驱动。** 打字用于说目标和提问；「开始」「继续」「提交」都是按钮，不经过模型，立即响应。
5. **只有一个下一步。** 任何时候回到首页，都只有一个明确的主操作。
6. **隐藏不等于上锁。** 简化只影响默认显示，链接、⌘K、问助手都能到达任何页面。
7. **卡片是回答的增强形式。** 整段对话都以回答为主，每条回答按内容带 0～3 张相关卡片，卡片不与某种意图一一对应。

## 3. 用户主线

主线是对话里**可能走出的一条路径**，不是必须按顺序经过的流程。用户可以一直只聊天，也可以从任何一条回答里的卡片进入；走上这条路径后，系统才给出明确的下一步。

```text
自由对话（回答 + 相关卡片）
  └─ 从卡片进入，或点「带我从最简单的开始」
       → 3 个小练习 → 动手任务 → AI 评价 → 第一段小结 → 继续第 1 章 → 了解完整课程
```

| 阶段 | 用户看到什么 | 这一阶段才出现的东西 |
|---|---|---|
| 1. 首次打开 | 开放的问题、输入框、混合示例（问产品、问知识、从最简单的开始） | 导航只有「首页」 |
| 2. 对话 | 助手正常回答，相关时穿插路线、小练习、课程等卡片 | 卡片 |
| 3. 小练习 | 从卡片就地展开；可以随时提问；完成后助手用简短回复接上下一步 | 「下一步」窄条、「我的」 |
| 4. 动手任务 | 右侧面板，对话留在左边，选择评价者后提交 | 「作品」入口 |
| 5. 评价 | 助手回复带结果卡；需要修改时可以补充后再交 | 逐条评价 |
| 6. 第一段小结 | 学到的要点、通过的任务、只含自己知识的小地图 | 「地图」入口 |
| 7. 下次回来 | 一句话 + 「继续」按钮 | — |
| 8. 走完第 1 章 | 助手介绍完整课程 | 完整路线、3D 课程树的提示 |

### 3.1 回答与卡片

**以下规则适用于整段对话，不只第一句话：**

1. **回答必须能独立成立：** 去掉所有卡片，文字仍然完整。卡片加载失败不影响阅读。
2. **每条回答 0～3 张卡片：** 卡片不与意图一一对应，没有「某种意愿对应某张卡」的固定关系。
3. **只放确实相关的：** 宁可不放，也不凑数。
4. **卡片跟着内容走：** 放在相关段落旁边，不统一堆在回答末尾。
5. **数据来自服务端：** 模型只提名卡片类型和对象；时长、进度等数字来自真实数据，回答文字不重复这些数字。
6. **卡片是可用的小对象：** 比如小练习卡就地展开来做，不只是链接。

**回答示例（举例，不是规则）：**

| 用户说的 | 回答的内容 | 可能带的卡片 |
|---|---|---|
| 「我想搞懂 Agent 怎么工作」 | 讲清 Agent 和普通聊天的区别，建议怎么开始 | 路线、课程章节 |
| 「什么是 Agent？」 | 直接回答 | 小练习、资料片段 |
| 「Agent 和 Workflow 有什么区别？」 | 讲清谁决定下一步 | 两个小练习 |
| 「我想让 AI 会查我们的文档」 | 解释原因和 RAG，如实说明第 3 章暂无小练习，建议先打基础 | 课程章节、路线 |
| 「我想看 ReAct」 | 说明它在哪，以及为什么要先学前面的内容 | 要点、路线 |
| 「我已经学过 Agent 了」 | 记下这个说法，但不算学习记录，也不跳过必需前置 | 路线 |
| 「我学到哪了？」 | 说明进度 | 进度（已开始时） |
| 「你能做什么？」「我想学点 AI」 | 简短介绍，或给 2～3 个方向 | 选项按钮 |
| 「今天好累」 | 自然回应，不推销课程 | 无 |

**对话的四条约束：**

1. **回答优先：** 用户问什么先答什么，引导放在回答之后。
2. **不追问：** 一次最多问一个问题，能用按钮就不用问题。
3. **不纠缠：** 引导一次后用户没接，就不再重复，等用户主动提起。
4. **始终有出口：** 开始学习前，常驻按钮「带我从最简单的开始」不经过模型，直接给出第一段路线；开始后由「下一步」窄条承担。这两个是界面固定入口，不属于回答。

**按钮操作的回复：** 点「开始」「完成」「提交」等之后，助手的简短回复用固定模板生成，不调用模型。它看起来也是对话，同样带卡片，例如做完小练习后回复要点并附下一个小练习。

**首版不做摸底：** 现有规则不允许跳过必需前置，用户自述有基础也不能产生学习记录。按基础调整起点需要摸底能力，不在本阶段。

## 4. 第一个打通的场景

使用《深入理解 AI Agent》（`ai-agents-in-depth`）第 1 章「Agent 架构与运行基础」，**不复制成新课程**，学习进度算在原课程上。

| 指标 | 数据（本地库） |
|---|---|
| 知识数 / 有微学习 | 10 / 10，全部单单元，每个 5～7 分钟，全章约 56 分钟 |
| 实践 | 6 个，每个 15～20 分钟（3 个 `instruction`，3 个 `workflow`） |

**第一段的范围：**

| 步骤 | 内容 | 时长 |
|---|---|---:|
| 1 | Agent：从回答到行动（A02） | 7 分钟 |
| 2 | 观察与动作：知道办法不等于做得到（AGC01） | 5 分钟 |
| 3 | ReAct：结果怎样改变下一步（R10） | 7 分钟 |
| 4 | 跑通最小 ReAct 循环（`book-v1-node-r10`，`instruction` 模式） | 15 分钟 |

通用代码不写这门课的标识（[course.md](../../rules/course.md)「Data-driven Frontend」）：起步段由导航决策和课程结构推导，首页示例和它们指向的课程放在数据库。

**内容的已知缺口：** 第 2 章只有 2/14 个微学习，第 3～9 章没有微学习。走完第 1 章后要如实告诉用户后面以动手任务为主；补微学习不在本阶段。查文档（RAG）在第 3 章，这类问题要如实说明，并建议先走第一段，见原型的「查文档」情景。

## 6. 核心机制

### 6.1 下一步只有一个来源

首页页头、窄条、「我的」面板、路线面板都读取服务端导航决策（`learnerStateService.getNavigation`）。删除现在分别拼出来的三处「下一步」：`LearningPage` 页头、`nextLabel`（第一个未验收实践）、`current`（第一个活跃知识）。

「今日」仍然只表示正在学的内容，不当作推荐（[learning-state.md](../../rules/learning-state.md)「Learner Entry and Today」）。

### 6.2 对话时间线与卡片

卡片是**回答的一部分**，不再由页面状态贴到时间线尾部，也不是一条消息附带的唯一结构化内容。

- **结构：** 一条助手消息由文字和卡片交错组成，直接使用 AI SDK 的 `message.parts`，不自定义消息格式：文字和工具调用本来就按顺序排列，卡片是展示工具的调用结果。现有 `structured_content` 每条消息只有一个对象，持久化方式在阶段 3 确定，并要兼容已有的 `course_search`、`course_creation_brief` 数据。
- **卡片按对象设计：** 知识要点、课程章节、路线、小练习、动手任务、评价结果、学习进度、知识地图、资料片段、课程匹配、创建简报。内容只存对象 ID，显示时读最新状态。
- **渲染：** 一个统一的卡片渲染入口，合并首页、档案、旧助手组件三套实现。
- **模型提名卡片：** 模型在回答过程中调用只读展示工具，只提名卡片类型和对象 ID；服务端校验权限后从真实数据生成，模型不写卡片内容，也没有改动权。提名无效时跳过卡片，回答照常显示。
- **不做固定的意图分类：** 回答什么、放什么卡片由模型结合工具结果决定，服务端只校验。不使用关键词表或正则（[course.md](../../rules/course.md)「Goal-driven Course Selection」的要求；原型里的关键词只是模拟）。
- **目标规划：** 模型判断用户在问学习目标时调用现有规划能力，结果作为课程匹配或路线卡片放进回答。模糊的目标使用已有的「需要澄清」状态。
- **按钮操作：** 写一条 `action` 类型的记录，再按模板生成简短回复和卡片，不调用模型。沿用现有 `message_kind = 'action'`，模型历史已经会过滤它。
- **传输：** 服务端从 `pipeTextStreamToResponse` 改为 AI SDK 的 UI 消息流，前端用 `useChat`，文字、工具进度和卡片按回答顺序交错传输。
- **会话：** 一个目标一个会话；已完成的卡片自动收起。

### 6.3 AI 评价（已选方案 A）

现状：提交后 `evaluateAssignmentResponse` 只产生 `pending`；前端选 AI 时根本不提交（`PracticeObject.tsx` 只显示预览）；`performance_results.evaluator_kind` 只允许 `rule` / `manual`。

**流程：**

```text
提交 → 记录不可变 Attempt + pending 结果（现有事务）
     → 服务端读取提交内容和评价标准
     → 模型按每条标准返回结构化判断（AI SDK 结构化输出 + Zod 校验）
     → 服务端校验，并由确定性规则得出结果
     → 追加新版本 PerformanceResult（evaluator_kind = 'ai'）
     → 沿用现有证据与掌握度规则
```

**约束：**

- **效力相同：** AI 与教师的结果语义、掌握度规则相同（learning-state.md 已规定）。
- **结果由服务端得出：** 全部标准通过为 `passed`，否则 `failed`（界面显示「需要修改」）。模型不直接给最终结果，浏览器也不能提交结果。
- **失败不伪造：** 模型不可用或输出未通过校验时保持 `pending`，提示重试或改交老师，不产生结果。
- **提交内容不可信：** 提交内容按数据隔离传给模型，其中的指令不执行；校验时要求每条判断能对应实际提交内容。
- **可追溯：** 反馈中记录模型、提示词版本和逐条判断。
- **独立于对话助手：** 评价是专用提供方（assistant.md 允许），助手只能解释结果，不能修改。
- **不增加 Function：** 放在现有 `api/learner.ts` 分发的 `api/_handlers/learning.ts` 里；评价作为独立动作，前端在结果产生前显示「评价中」。
- **成本与滥用：** 按用户和实践限流；相同内容的幂等提交不重复评价。

**首版只评价文本、`.txt`/`.md`/`.csv` 和链接说明。** 第一段的任务是 `instruction` 模式，够用；工作流提交的评价后续再做。

### 6.4 技术选型

原则（[AGENTS.md](../../../AGENTS.md)「Infrastructure Reuse」）：协议、流式传输、校验、渲染等基础能力使用成熟的开源组件；EduFlow 只保留产品语义、权限、校验和学习规则。本次改造不自造框架。

**继续使用的现有技术：**

| 领域 | 技术 |
|---|---|
| 前端 | React 19、TypeScript、Vite、React Router |
| 后端与数据 | Vercel Functions、Supabase（Postgres、Auth、Storage、RLS） |
| 大模型 | Vercel AI SDK（`ai`）、Zod |
| 可视化 | three.js、React Flow、ELK |
| 内容 | Tiptap、PDF.js、KaTeX、H5P |
| 测试 | Vitest |

**替换或新增（版本和许可证于 2026-11-05 查自 npm，均未在项目中试用）：**

| 现在 | 问题 | 改为 | 许可证 | 阶段 |
|---|---|---|---|---|
| 手写读流（`assistantClient.ts`）和消息状态（`AssistantRuntimeContext`） | 只能传纯文字，出错和重试都要自己管 | `@ai-sdk/react` 的 `useChat` | Apache-2.0 | 3 |
| 纯文本流（`pipeTextStreamToResponse`） | 传不了卡片和工具进度 | AI SDK 的 UI 消息流 | Apache-2.0 | 3 |
| 自定义「文字和卡片交错」结构 | 重复造轮子 | AI SDK 的 `message.parts` | Apache-2.0 | 3 |
| 手写 Markdown 解析（`renderAssistantText`） | 语法有限，流式输出时容易显示错 | `streamdown`；包体积过大则用 `react-markdown` + `remark-gfm` | Apache-2.0 / MIT | 3 |
| `@ai-sdk/openai-compatible` 接 DeepSeek | 阶段 0 已证实与协议文本泄露无关 | **不因此更换。** 同时清理名不符实的 `dmxapi` 配置和 `thinking` 选项（去掉后泄露率降低，但不是根因） | — | 1 |
| 没有结构化评价能力 | AI 评价需要可靠的结构化输出 | AI SDK 结构化输出 + Zod | 已有依赖 | 2 |
| 依赖中没有浏览器测试框架 | 主线回归需要 | `@playwright/test` | Apache-2.0 | 5 |

**需要自己写的（产品逻辑）：**

- 卡片的内容和界面（符合设计规范，读取真实学习数据）
- 服务端校验和权限
- AI 评价的提示词，以及由逐条判断得出结果的规则
- 下一步和逐步导航的判断（复用现有导航引擎）

**考虑过但不采用：**

| 方案 | 原因 |
|---|---|
| `@assistant-ui/react` | 仍是 0.x；界面要按设计规范重写，`useChat` 已够用。以后需要附件、分支对话时再评估 |
| Vercel AI Elements 等组件 | 依赖 Tailwind 和 shadcn，项目没有使用，且有自己的设计令牌 |
| LangChain 等 Agent 框架 | AI SDK 已覆盖工具调用和多步执行 |
| 专门的提示词评测平台 | 首版用 Vitest 加真实对话样例，样例多了再考虑 |

**引入前要核对：**

- `streamdown` 的实际包体积。
- `@ai-sdk/react` 要求 React `^19.2.1`（项目声明 `^19.2.0`），并与 `ai` 对齐版本（项目 7.0.79，npm 最新 7.0.163）。
- 手写的 `api/_lib/llm.ts`：课程创建提案如何生成结构化结果，能否合并到 AI SDK。
- 依赖改动按 AGENTS.md 用 pnpm 更新锁文件，`pnpm install --frozen-lockfile` 必须通过。

## 7. 实施计划

### 阶段 3：时间线与卡片（2026-11-06 本地验收通过，未提交，未部署）

**实际决定：**

| 对话自由后，用户聊很久也没开始学习 | 首版只靠常驻按钮，不追问；上线后看「第一句话类型 → 是否进入第一个练习」，再决定是否加强引导 |
| 模型提名的卡片错放或漏放 | 回答不依赖卡片；提名无效就跳过；用对话样例回归；常驻按钮兜底 |
| 卡片过多，对话变成推荐信息流 | 每条不超过 3 张；样例中检查相关性；不做意图到卡片的固定映射 |
| 文字和卡片数字不一致 | 回答文字不重复卡片数字，数字只由服务端生成 |
| 对话跨多天变成长日志 | 卡片自动收起；窄条常驻；一个目标一个会话 |
| AI 评价不准，直接影响掌握度 | 判断必须对应提交内容；用真实提交做一组评价样例；上线后抽查 |
| 模型费用上升 | 按钮不走模型；评价限流；幂等不重复评价 |
| 用户走完第 1 章后内容断层 | 如实说明；后续按学习数据决定优先补哪些微学习 |
| 现有工作流依赖 3D 课程页和档案 | 只改默认入口，功能和路由不动 |
| Vercel Function 数量上限 | 不新增 Function，放进现有处理逻辑 |
