# EduFlow 端到端学习体验设计｜五步审查草案

> 状态：**设计提案与静态情境核验**，不是已上线功能，也不是浏览器端到端验收。
> 基线：`feature/project-capability-model`，2026-10-12 仓库核查。范围：优先普通学习者，设计兼顾课程创建者/企业管理员权限；不修改产品代码、数据库、已存在的权限或运行契约。
> 本稿回应的关键修正：**微学习和练习以独立交互、模拟操作、实操结果/文件提交为主体；局部助手只在用户需要时提供讲解、提示、纠错与调整建议，不能替代任务执行。**

## 0. 固定设计原则

1. 用户可经统一入口自由交流、跨课程讨论，**课程不属于聊天会话**；正式操作必须有明确归属。
2. 一个共享的助手运行机制；全局会话与任务工作区会话可以不同。共享身份/受控上下文引用，不互相拼接整段消息。
3. **微学习与练习不是对话的子类型**。微学习主体为分步讲授/操纵/小测；练习主体为模拟、工作流、操作或实际成果提交；助手为可召唤的辅助侧栏。
4. 每次有业务意义的操作保留 `user/course/action/attempt/source` 的正式身份和来源。全局聊天只保存交互，不自动变成证据、进度或能力。
5. 区分 `内容资源`、`行动执行`、`表现结果`、`正式诊断`、`能力确认`、`路线版本`。各自权限和确认步骤不能绕过。
6. 同一记录可投影成“全局时间线 / 课程时间线 / 能力证据线”，不建立互不一致的三套真值源。
7. 任务可以暂停并从权威进度恢复；切换项目不破坏未提交草稿、历史提交、原会话。
8. 界面可简化，**不能把业务边界合并为一个万能消息/卡片处理器**。

## 2. 完整用户旅程

### J1 首次进入与创建学习目标
登录→统一首页看当前目标/建议（新用户为轻量引导）→输入自然语言目标→解析目标并澄清必要条件→检索复用课程/创建个人课程→确认目标范围→进入项目能力图→展示可执行下一步。未确认方案不能当作正式项目修改；空白聊天也可自由提问。

### J2 日常学习与微学习
首页推荐任务卡/能力图→打开 Micro 工作区（**主区域是分步互动**）→按需开启侧边助手解释概念或给步骤提示→继续点击/拖动/选择等正式微学习交互→系统按微学习自身规则判定进度→保存进度及允许的学习事实→工作区显示继续/重学/返回项目→首页呈现事件卡。助手文本不是作答或达标证据。复习不重复写首轮完成证据。

### J3 实践、模拟、成果提交
首页/项目选择 Practice→工作区以模拟器、操作步骤、文件与成果提交为主体→用户可向侧边助手询问任务含义、工具用法、思路调整（辅助意见不自动改评分标准）→保存草稿、继续操作→**显式提交**产生 Attempt 与 Result（可能 pending/failed/passed）→可人工/正式评价→如有有效证据，经独立诊断和确认更新正式能力→关联项目路线的下一步建议；不能由“助手说完成了”代替提交。

### J4 多门课混合对话与记录归属
全局对话提及 A/B 两门课→用户可自然讨论两个项目，无须切换聊天窗口→需要开始正式活动时，助手显示**各自有项目/任务身份的行动卡**→点击 A 卡进入 A 任务，B 卡仍可稍后执行→分别产生 A/B 活动历史→全局学习历程按时间显示，课程过滤不改变原记录→同义能力但不同标准不得直接合并达标结果。无确定身份时先确认，不静默落到“当前课”。

### J5 调整课程、目标和路线
在对话提出“缩短基础部分/补实操练习”→区分个人训练顺序调整、个人课程定义修改、组织共享课程修改、目标能力修改→生成预览差异与影响范围→查权限→显式确认→分别调用原有保存/发布或 Preview→Adopt 契约→保留历史版本与旧 Attempt/Result→重新计算可执行下一步。**课程改动不自动等于个人正式路线采纳**。

### J6 上传资料、更新个人能力
在对话或任务界面上传→展示用途：当前问答参考/课程资料候选/任务提交工件/能力相关外部证明→按不同权限与来源持久化→若作为任务工件，走正式 Attempt；若作为外部能力证明，走证据源→诊断→提案→用户确认→能力更新；若只是课程参考材料，只更新资源候选，不触发能力写入。上传失败保留当前输入和任务草稿。

### J7 恢复与回顾
次日打开→首页显示可继续任务和相关项目进展→点击“最近活动”进入业务事件细节，可按权限回到原任务/审阅提交结果/查看可选的辅助会话片段→不需要恢复上次整个全局聊天才能继续任务。能力状态按事实及对应的评价/确认版本呈现。

## 3. 交互、状态与上下文关系

### 3.1 责任模型
- **全局助手会话**：开放问答、意图协调、可检索项目/状态的说明与操作建议。含多个项目完全合法，不以 courseId 强制限定整段会话。
- **项目/课程**：目标、能力范围、训练/评价定义和当前路线。继续沿用仓库现有 Course/Knowledge/Route 领域语义，不为交互重新造 Project 表。
- **Action/任务工作区**：任务定义 + 运行身份 + 草稿/执行进度；正式执行归 ActionRun/Micro 进度/Assignment Attempt 等现有职责。
- **工作区侧边助手会话**：与当前任务范围绑定、按需出现，只提供帮助/解释/建议；**不是任务主界面**，不可以绕过正式提交/确认。
- **学习历程**：从已有权威事件/运行对象**读取并投影**为多种视角。若未来需要聚合索引，必须是可重建的读模型，不做第二真值源。

### 3.2 主对话与局部助手怎样关联
1. 主对话任务卡保存最小、可校验引用：`courseId + actionId + [actionRunId / microPathId / assignmentId]`，以及拥有者/时间；服务器重新验证归属。
2. 进入任务后，从原任务状态加载上下文；**不传整个主对话历史**。只传必要的目标、任务定义、合法资源、用户明确提交的补充背景。
3. 工作区助手有自己的对话上下文和恢复标识；离开/重开任务可以重用它，但不得让其自由跨越其他课程的私有资料。
4. 任务结束后，主对话可显示一张“任务已提交/等待评价/有新评价/下一步建议”卡片；卡片读取实际业务记录。**不把局部助手聊天复制进主对话当证据**。
5. 全局助手如需解释某次结果，通过授权读取相应 Result/Diagnosis/事件摘要；只有用户主动查看时才按需展示局部聊天内容。
6. 若一条全局消息提到多个课程，消息按会话历史保留一份；它衍生的不同任务操作分别绑定对应业务归属，不能把消息硬分配到单课程。

### 3.3 正式状态变更守则
| 输入或行为 | 可改变 | 不得直接改变 |
|---|---|---|
| 闲聊/问答 | 会话历史、临时意图 | 任务完成、证据、正式 UKS、路线 |
| 微学习按步骤完成 | Micro 进度与既有契约允许的学习状态 | 直接宣布 mastered；复习重复发证据 |
| 模拟练习/文件显式提交 | Attempt、Result、Run 执行状态 | 跳过正式诊断/确认改 UKS |
| 外部能力证明 | EvidenceSource、Diagnosis、Proposal | 未确认 UKS；自动 Adopt 路线 |
| 课程编辑预览 | 提议与差异 | 未授权正式课程、历史尝试 |
| 正式课程修改确认 | 有权限的课程版本/定义 | 无确认改个人 Route、抹掉历史 |
| 个人路线预览与采纳 | Preview 后显式 Adopt 生成路线版本 | 修改 Knowledge 事实或 UKS |

**特殊情境**：`pending` 是待评价而非失败；`failed` 是本次表现，不能被辅助助手措辞覆盖；课程结构变动导致旧任务失效时保留历史并显式提示重新规划。

## 4. 信息架构与页面流转

### 4.1 一级入口（建议）
- **首页·学习助手**：唯一主输入框、当前目标/项目选择、下一步行动卡、最近学习活动。默认突出“继续目标”，而非空白聊天。
- **项目详情**：能力图、现状/目标差距、正式路线、训练任务目录与课程编辑入口。
- **学习历程**：全局/按项目/按能力过滤的业务事件流，结果详情深链。
- **资料与能力**：用户可访问的资料、个人能力和证据源；编辑权限依角色。
- **任务工作区**（上下文页面而非固定一级导航）：Micro 以交互为主；Practice 以模拟、操作、成果为主；辅助助手按需展开。

### 4.2 主/任务示意
```text
首页（主对话、当前目标、行动卡、学习历程预览）
 ├─ 项目能力图 → 选取行动 → 任务工作区
 ├─ 对话提出新目标 → 澄清/搜索/预览 → 项目详情
 ├─ 上传资料 → 用途选择/提案 → 课程或证据流程
 ├─ 学习历程 → 某次 Attempt/Result/诊断 → 原工作区详情
 └─ 任意项目切换 → 主对话保留；正式任务范围明确

任务工作区
 ├─ 主体：微学习操作 / 模拟 / 实操提交
 ├─ 侧栏：可展开助手（上下文已绑定任务）
 ├─ 暂停/保存 → 返回首页（任务可恢复）
 └─ 正式完成/提交 → 结果 / 待评价 → 首页事件卡
```

### 4.3 界面承载规则
- 简单的一次性知识提示/选项可在主对话内卡片处理；有进度、评价、模拟、操作环境或可恢复草稿的活动进入工作区。
- 正式提交入口必须属于任务工作区；聊天输入不伪装成提交按钮。
- 助手建议改变任务流程时只能修改**草稿建议**或导航建议，不得隐式修改已发布规则、评价结果或个人能力。
- 工作区手机窄屏使用浮动“问助手”抽屉，不让助手与主要操作平分屏幕；桌面右栏可折叠。
- 管理员/课程作者的编辑功能允许复用助手作解释，但编辑、预览、应用仍在有权限的工作区完成。

## 6. 开发前必须审议的三个决定

1. **单一主对话的表现形式**：是否保留一段永久滚动会话，还是视觉上单入口但服务端自动分段？建议后一种，不抹掉历史；具体分段策略不进入本轮代码。
2. **学习历程聚合策略**：复用现有学习事件/结果投影，确定排序与多课程归属后，再决定是否新增物化读取索引；不要提前建新权威历史表。
3. **修改权限与范围**：个人路线调整、个人课程更改、共享课程发布及能力模型治理使用各自现有权限流程，统一助手只发起提案。
