# EduFlow 助手

> 由 AGENTS.md 拆出。修改本领域代码前必须阅读本文件；与 AGENTS.md 冲突时以 AGENTS.md 为准。

## Global EduFlow Assistant

- Learner-facing Assistant/chat surfaces MUST use the one Global Assistant runtime. Pages provide explicit `AssistantContext` identities and MUST NOT introduce page-specific learner LLM runtimes.
- Contextual Assistant and Full Chat share the authenticated session/message model, server execution boundary, tool registry, model adapter, and policy. Each historical message persists only a small identity snapshot; the browser MUST NOT send complete product entities as authoritative context.
- Assistant entity and learner-state access MUST be revalidated server-side through authenticated product data. Browser-supplied user IDs, roles, capabilities, or context payloads are never authority.
- The deterministic Navigation Engine owns the server decision and teaching order. The Assistant MUST read it through a read-only tool (`getNavigationDecision`) and MAY combine it with the conversation when advising what to do next; it MUST NOT invent a next object or mark unlearned content as learned, skipped or complete. A navigation read MAY lazily materialize the existing V1 route. CurriculumSequence, AssignmentDependency, KnowledgeEdge, Course progress, and Learner Knowledge state MUST retain their distinct meanings in Assistant tool output and answers.
- Specialized authoring, mutation, generation, and evaluation providers MAY remain separate, but Learn-mode explanation and retrieval use the Global Assistant runtime.

## Answer cards and protocol safety (2026-11-07)

- The Assistant streams AI SDK UI message parts. An answer is the actual ordered sequence of text, tool-progress and read-only display-card parts; nothing written before a tool is discarded, merged or restored later. The model never writes card content. It nominates a card type and existing object IDs through one display tool (`displayCard`), and the server revalidates visibility, existence and the learner's state before building title, duration, progress and status from real data. Live stream, persisted parts and a refreshed conversation are the same sequence.
- The model decides whether a card is useful and where it belongs from the component directory generated from `componentCatalog.ts`; there is no fixed per-answer card count, server-preselected candidate list, intent classifier, keyword table, regex mapping or "question type → card type" rule. Zero cards is normal for a plain explanation, small talk, a meta question or when no real object was found. An invalid or unavailable nomination is skipped and the answer continues. The prose MUST remain complete without the cards, MUST NOT repeat their numbers, and MUST NOT be used to advertise a Course during small talk or a plain question.
- The model finds card objects through ordinary read tools (`searchKnowledge`, `searchMicro`, `getCourseContext`, `searchMaterials`, `getMaterialContext`, `getNavigationDecision`, `getLearnerState`, `getAssignmentContext`, …) or uses identities already in the explicit context. When choosing a 小练习 it prefers the current Course and every result states which Course it belongs to; a card for another Course the learner can see is allowed.
- A 知识点 card is the Archive/Course Knowledge node: node title, node status label (`knowledgeStateLabel`) and a small dot. It is not a Micro, never renders or starts practice, and opens `ArchiveNodePanel` in the Home right panel without leaving the conversation; the Home panel reuses the Archive graph loading path. A 小地图 card draws one Knowledge node's real neighbor edges from the shared graph with a deterministic layout; it opens the Archive focused on that node. Presentation state never relayouts it.
- Cards are stable: every card stays in the answer that placed it. Status changes update the same card in place and never hide, replace, collapse or move it; a completed 小练习 keeps its full card and shows its real step list with green checks. The card the learner opened owns the runner; there is no "latest card only" rule. 小练习 form (inline/side/immersive) and its owning card are part of the URL and survive reload.
- Opening, starting, submitting and completing a learning object MUST NOT append an operation or template message to the conversation. The assistant learns those states from the next request's server-validated context and real product state. Existing `message_kind = 'action'` operation rows are hidden from the timeline; structured Course Search and Course Creation Brief rows remain readable.
- Protocol text is guarded while streaming: a suspicious trailing prefix is held, released when confirmed safe, and a complete marker aborts that generation. The server retries once; failure shows the existing retry state. Protocol text MUST NOT reach the UI or the database.
- A reply can be stopped by the learner. The composer stays editable during a reply and its send control becomes stop; Enter never sends or clears the draft while replying. A stop keeps what was already generated, marks it as stopped, survives reload and never triggers an automatic retry or reply polling. Incomplete text that was stopped by the learner is distinct from a failed generation.
- Persisted card parts store object references only. Model history replays displayed cards as standard AI SDK tool-call/tool-result messages whose result is a compact label, never as prose the model could copy; card payloads and learner-facing marker text are not sent. Operation rows remain excluded. Legacy `[此回复展示的卡片：…]` markers are stripped from streamed, persisted and historical text by the existing protocol guard.
- The composer shows the current object identity as a removable context tag. Removing it excludes that identity from the next server request and the object panel stays open; acting on the panel again restores it. A failed question MUST NOT be answered again in the next reply; unanswered trailing user rows are excluded from model history and, once a later question exists, show one grey 「没有回复」 line under the failed turn.
- Batch 2 adds learner-owned write tools: `submitAssignment` and `withdrawAssignmentSubmission`. The model decides intent from the conversation; code validates only published Course, Assignment existence/eligibility, attachment ownership and input shape. A clear submit calls the ordinary immutable Attempt + evaluator transaction; 「帮我看看」 only reviews; genuinely unclear intent gets one short question. No confirmation card is added. The original task card updates from live state and the answer may add a compact one-line task card backed by the same object reference. Withdrawal has no dedicated server-injected "latest attempt" prompt: like any other write, the model reads `getAssignmentContext` (`submissionSummary` and `mySubmissions`) and passes the exact Attempt it means.
- The composer adds files and links with `+`, drop or paste. Upload reuses `user_evidence_sources` and `user-evidence`; the server revalidates type (`.txt`/`.md`/`.csv`), size, ownership and parse state. Text content is read server-side for the model. Images/PDF are not presented to a model that cannot read them; the UI says so instead of pretending. An unsaved panel draft may accompany a turn as untrusted context because it is not durable learner state.
- Assistant features register as plugins (tools + cards + existing panel). The display tool is the single card-nomination surface and the render layer is replaceable. Tool calls persist as compact, collapsible progress labels, never payloads. Every plugin tool marked as a write emits the same structured `data-write-result` part for success and failure; the part comes from the tool output, never from model prose. Next-turn model history replays it as a standard tool result. After an answer the model MAY offer 0–3 follow-up suggestions. Clicking one only fills the composer (newline-appended when a draft exists, cursor at the end); it never sends. There is no fixed suggestion strip.
- A model-called `openWorkspacePanel` opens the existing assignment, route, reader, records, My or map panel and appends no operation message.

- Vocabulary: 小练习 is the Course's interactive Micro; 动手任务 is a Course Assignment whose work is submitted to an evaluator. Interface copy, prompts, the card directory and follow-up suggestions MUST use this distinction. A model-written temporary exercise is explanation only, is never a card and never enters a learning record.

## Unified EduFlow Assistant

- The product has one user-visible EduFlow Assistant identity and shell language. Workspace, experience mode, active context, role, and capabilities determine available actions; Feature-specific providers may remain behind adapters.
- Assistant mutation requires both Design Mode and the existing capability checks. Proposal preview, deterministic validation, Apply, and Undo MUST NOT be bypassed by the unified shell.
- Learn and Explore Assistant actions may explain, recommend, focus, or start supported experiences, but MUST NOT expose curriculum, material, publication, or Domain mutation without the corresponding authority and validation path.
