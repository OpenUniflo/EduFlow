## Project Capability and Personal Route V3

- Candidate capability space and selected personal route MUST be separate pure computations over explicit visible graph, Course coverage and user-state inputs. Project targets remain all active CurriculumCoverage Knowledge IDs.
- hard prerequisites are AND gates; soft prerequisites MUST NOT block Navigation or Micro and MUST NOT enter the default necessary route merely as recommendations.
- Default selected route is retained targets plus recursive hard closure to satisfied boundaries. Include requires the Personal Route to pass through a capability already in the current Project Capability Model; it MUST NOT expand the model. Intermediate selected nodes MUST participate in selected factual paths; current Project route entries must be formally acquired; historical Node Actions retain their executor/history contracts and never invent incoming Edges. Exclude forbids using even acquired support. Invalid constraints MUST return structured root/support conflicts; all targets excluded is valid and MUST NOT trigger a curriculum fallback.
- Personal route versions MUST be immutable, user/course scoped and atomically appended with optimistic base-version checking. Only initialization, explicit adoption and restore create versions. Versions MUST persist reference-only Node/Edge scope, selected Action and execution order decisions. Restore MUST revalidate historical constraints and Action choices in the current world and MUST NOT silently substitute choices or roll back learning/history.
- Adopted execution snapshots own formal route membership and choices; server revalidation diagnoses invalidity without dynamically replacing them. Course Route uses the restored sequential Step UI; its connectors are execution order, never KnowledgeEdges. Project Capability owns node/Edge/Action planning and Preview; Action-only changes require Preview and Adopt. Server revalidation owns execution eligibility. Client selected/ordered/bridge lists MUST NOT authorize learning; original Course coverage MUST NOT bypass active Exclude. Micro RPCs MUST remain service-only and check expected active version and hard eligibility.
- Project colors are blue acquired, green pending target and gray pending intermediate; this project-only encoding MUST NOT replace Domain color in the Archive. Same-structure state, draft, Preview and version changes MUST NOT recompute layout.
- The Project Capability Model is presented in the course 3D scene: course Knowledge on the front plane, non-course ancestor Knowledge of the model on deeper planes directly behind the course Knowledge it supports — hidden in the front pose, revealed by rotation. No container plate or frame is drawn around a layer. The current route is a directional pulse beam through both planes.
- Route editing flattens the model into a deterministic layered 2D layout (columns by factual dependency depth: acquired → intermediate → targets). Flattening animates the same node set and MUST NOT change the model node/edge set; layered positions are a pure function of model structure.

- Project Capability Model is the union of legitimate candidate target paths over active visible factual prerequisite/enables relations, formal UKS and Course targets. It supports multiple roots, branches and merges, with entries only at formally acquired capabilities. Gray members must be acquired-reachable and reach an unfinished target, with incoming and outgoing factual relations; unacquired roots are excluded. All anchored branches through acquired intermediates remain candidates. Unrelated isolated nodes and related relations MUST NOT enter it. Missing Action resources MUST NOT remove capabilities or facts. Normal, Editing, Preview, Hover, Search and Inspector MUST share identical model node/edge sets under the same UKS. Formal UKS changes MAY change the model and layout only when its structural set changes, but MUST NOT create Personal Route Versions automatically.
- Project node selection MUST highlight the complete visible directed downstream subgraph with presentation-only pulses, independent of color/role, without changing graphData, force layout or camera. Normal Project view is canvas-first; route version/Include/Exclude/Preview tools appear only in route editing mode. Narrower candidates MUST revalidate old constraints explicitly without mutating immutable history.

- Project Capability support MUST explicitly preserve hard/soft prerequisite and numeric-strength enables. Related MUST NOT enter project structure or downstream pulses. Enables MUST NOT be cast to soft RoutePrerequisite or enter hard closure, Navigation or Micro gates.
- Current support MUST use a deterministic cycle-safe least fixed point seeded exclusively by formal acquired capabilities; factual roots without acquisition do not seed the Project Model. Hard prerequisites remain AND constraints; soft/enables MUST NOT become hard gates. Enables cycles MUST NOT bootstrap themselves without a legitimate entry.
- Course generation/creation MUST report targets isolated under prerequisite + enables for evidence/scope review, never fabricate edges or require a single component. Project pulse is presentation-only continuous beam/packet rendering; per-frame work MUST NOT rebuild graph data or traverse topology.

## Route Execution Presentation (2026-10-05)

- Project ordinary KnowledgeEdges MUST use one solid line visual; prerequisite/enables semantics remain in data and details. Candidate Action branches MAY use dashes.
- Current and Preview routes MUST use directional source-to-target presentation pulses over factual Edges without topology, force position or camera changes. Reduced motion uses static highlights and arrows.
- Project default Route node rings MUST NOT render; Global/Personal learning and mastery rings retain their existing meaning.

- Course-owned AssignmentCoverage may reference active, visible Bridge Knowledge that supports course Knowledge through factual prerequisite/enables ancestry. It MUST NOT imply CurriculumCoverage, CourseTargetKnowledge, or a synthetic KnowledgeEdge; unrelated, related-only, and inaccessible targets MUST be rejected.

## Capability Action Scope and Execution V3

- Capability Actions have exactly one Node or factual Edge scope, with only micro_learning and practice_task types. Existing ActionRun, Result, Evidence, executors and course bindings MUST be reused. Node scopes MUST refer to legitimate route roots and MUST NOT bypass intermediate factual prerequisites.
- Each selected scope has 1..N distinct Actions executed consecutively in user-defined local order; global order is display/recommendation only, never a cross-scope gate. Node Action completion grants derived route execution reachability, never UKS or mastery. Acquired Nodes are satisfied without fabricated completed Runs.
- Edge execution retains reachable-source, same-scope order and hard incoming conjunction semantics. Independent roots and Edges MAY be available concurrently.
- Scope-less historical executionSteps MUST remain Edge Steps without rewriting snapshots. Applied migrations remain immutable; database changes MUST be forward migrations retaining old Edge rows, runs and history.
- Preview and Adopt MUST revalidate structure, all scope Actions, resources and fresh formal capability state on the server. Evidence → Diagnosis → Proposal → explicit Confirm alone changes UKS; Preview → Adopt alone adjusts an established Personal Route.
