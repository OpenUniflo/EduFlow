## 3. 方案设计

### 3.1 P0a：统一表单语义与提交门禁

**显式产品决策：A 与 B 不可混称。**

| 选项 | 契约含义 | 三类操作结果 | B/C 兼容性 |
| --- | --- | --- | --- |
| A | required 表示属性必须存在；允许空文本时，新建表单草稿显式提供 `""` | 未输入、输入后删除、正常 JSON 往返均保留 `""` | 兼容当前 B `comment`、C `finalNote`；C 可继续用空字符串选择模型草稿 |
| B | “可留空”表示可省略，将属性移出 required | 未输入为缺失；删除回到未设置；JSON 省略也为缺失 | 改变定义；省略字段不会产生对应 `resumeWrites`，必须检查下游语义 |

**已确认采用 A（2026-10-21），兼容现有 B/C；B 保留为未来字段级选项。** 文案统一为“允许空文本”；新字段默认必填，作者可显式勾选“可省略”（B）。不得根据字段标题中的中文关键词推断契约，也不批量更改已保存定义。

> 已确认：A 的自动初始化**只用于人工回应草稿**；启动输入仍以缺失为默认，用户可显式选择“提供空文本”。不得把“未提供”静默变成“显式空值”。

A 的初始化只作用于新建人工表单草稿中明确类型的 required 普通字符串，排除 enum、const、联合分支和未创建的可选对象；不向历史快照、调用方输入或 JSON 显式删除的属性偷偷补值。`minLength: 1` 即使初始化为 `""` 仍校验失败。JSON 主动删除 required 属性属于用户改变有效载荷，必须报错，不能宣称它与正常往返等价。

统一规则：

- 缺失与 `null`、`""` 分别表示；只有 Schema 允许才接受 `null`。
- `false`、`0`、`[]` 原样保留；是否有效由类型、范围、`minItems` 等约束决定。
- optional 字段提供明确的“未设置/省略”状态；显式空文本与省略不能静默互换。
- 不自动 trim、类型转换、填充业务默认值，不替用户选择批准或拒绝。
- 表单与高级 JSON 使用同一 canonical 值；无效 JSON 保留编辑原文并阻止提交，不能使用旧有效值运行。

`SchemaForm`、运行表单与 `NodeResponseForm` 共用值处理和 Schema 校验；人工回应保留已有额外约束。当前回应检查位于 `src/features/workflow/editor/v2/NodeResponseForm.tsx:13`，服务端检查位于 `services/workflow/src/eduflow_workflow/interrupts.py:27-35`。

脚本 `scripts/workflow/examples/create-agent-scenarios.mjs:24` 的 `obj()` 改为显式接收 required 集合；新生成 B/C 保持所选语义，既有数据库定义不自动更新。场景 A 的订单号、诉求非空约束保留，其“类似问题”须定位具体字段后才归因。

**提交门禁。** 增加运行准备对话框：输入合法后才能确认提交，随后沿用服务端 preflight → 必要保存 → 创建 Run。取消填写不保存、不创建 Run；预检期间取消须使迟到响应失效；保存已经完成时允许留下已保存修订，但禁止继续创建 Run。提交已发出后进入“状态待确认”，不得把关闭窗口宣称为撤销成功。

P0a 只交付“不创建 Run 的最小门禁与运行准备对话框”；Start 编辑区、消费者视图、可选输入/空对象体验在 P1a 完成。

沿用提交快照、幂等键、409 冲突与未知提交恢复机制，避免读取尚未提交的 React 状态。

### 3.2 P0b：人工审核最小安全上下文

在回应表单前展示四块信息：待审对象、必要依据、关联输出、批准后的动作与范围。

- A：订单与诉求、实际查询结果、待审建议、后续动作。
- B：当前维度及调用、该项结论、项目约束、回应影响项。
- C：已确认记录、本轮进展、待保存稿件、目标项目范围。

> 已确认（2026-10-21）：按上述 A/B/C 四块展示；关键依据缺失或身份无法确认时，只允许拒绝/取消，禁止批准。

上下文由本次冻结定义、绑定及授权执行记录确定，不用当前最新定义或同名节点最近输出猜测。身份关联至少包含 Thread、当前 Run、checkpoint、interrupt、task、namespace；graphPath 只标识图位置。

切换任务时上下文、回应草稿与提交目标同步切换；刷新后重新读取当前等待身份；延迟响应不得覆盖新选择。缺少关键待审对象或身份无法确认时，禁止批准并解释缺失，不用空面板诱导确认。批量回应也须逐项满足条件。

优先利用现有记录做受限投影。若需 API 补充，只扩展现有只读边界；前端隐藏不构成授权。不得返回整份 State、凭据或其他任务数据。是否需要改变 worker，须以字段可用性核查为准，不预设新增 interrupt 持久契约。

### 3.3 P1a：Start 契约与启动交互

`definition.inputSchema` 仍是唯一启动契约；`state.inputBindings` 仍负责初始化映射。Start 配置区只是其编辑入口，不在节点 config 复制 Schema，也不强制 Input 全部进入 State。P1a 在 P0a 的门禁之上补齐 Start 编辑入口、消费者视图和可选输入体验。

启动流程：点击运行 → 有输入时打开对话框 → 字段检查 → 原有服务端 preflight → 必要的保存确认 → 创建 Run。取消收集阶段不创建 Run；请求已提交后的取消属于现有运行取消语义。

**启动输入不自动补 `""`**：字段留空仍按缺失处理；只有 Schema 允许且用户显式选择“提供空文本”时才提交 `""`。这与人工回应草稿的 A 初始化不同，界面文案和校验提示必须区分，不能共用一个“可留空”标签。

只有确认无输入契约且 `{}` 合法时直接启动。存在可选输入字段仍允许填写，并提供“使用空对象运行”；不能仅因没有 required 字段就跳过表单。通用或无法生成表单的 Schema 保留高级 JSON。

**移除运行 tab 常驻“本次运行输入”编辑表单**，对应 `src/features/workflow/editor/v2/LiveWorkflowEditor.tsx:452`。运行 tab 仅保留执行结果、历史、下一轮输入；可在历史详情展示只读启动摘要，目的是解释本次结果与输入来源，不成为第二个编辑入口。

四类标签固定：

1. **启动输入**：Start 声明、启动对话框填写。
2. **节点输入绑定**：节点配置展示来源，State 单独标为“共享状态”。
3. **人工回应**：当前等待任务入口。
4. **下一轮输入**：会话后续轮次入口，不冒充恢复回应或初次启动参数。

消费者视图同时列出直接 `source: input` 消费节点和 inputBindings→State 映射，标注后者可能被后续写入覆盖。场景 A 应明确显示 `prepare` 读取 `/orderId`、`/question`。

**Assignment/API 边界为确定要求：** 输入由调用方提供；画布只读展示授权快照，不能手工覆盖权威输入。服务端重新验证身份、launchContext、Schema 与调用来源约束，不能只依赖禁用控件。当前 `api/_lib/workflowV2.ts:96-110` 的 `validateLaunch` 已验证 Assignment 关联资格，`:312-315` 在创建 Run 时再次做编译与 Input 校验；但不能据此认定字段级权威输入保护已经完整。

> 这里区分的是**访问上下文**，不是两个不同的人：同一用户在 Assignment 执行上下文可以填写/提交调用方提供的输入；查看自己的历史 Run 时只读。历史仍归属该执行用户，不另设“观察者账号”。

若允许复制为手动调试，必须明确创建独立调试调用，不继承正式 Assignment 归属。运行成功不自动完成 Assignment 或授予 mastery。

历史复用沿用 `api/_lib/workflowV2.ts:68-70` 的输入投影。敏感字段已移除时必须提示补填，不把脱敏占位符当实际值，也不称为“相同输入”。真正相同输入重跑还须明确冻结版本，重新校验；不保证外部工具输出相同。

### 3.4 P1b：语义摘要与子图调用历史

气泡按消息、工具调用、评审结果提供确定性摘要；区分“读取、返回、写入”，保留展开详情，不调用 LLM 生成解释。替换 `src/features/workflow/editor/v2/executionPresentation.ts:15` 的通用截断优先策略，未知结构保留安全降级。

子图按父 Thread/Run、图路径和真实调用身份组织，不按 nodeId 或 graphPath 合并。现有 `SessionHistoryWorkspace.tsx:36`、`:46` 已支持 namespace 查询和选择，应复用；它尚不等于整张子图的调用实例视图。

## 4. 验收标准

本轮验收分两层：**4.1 技术与回归验收**由实施/验证角色执行；**4.2 无背景普通用户验收**由未参与实施的普通用户独立执行。两层都通过才算本轮完成，技术通过不能替代体验验收。

### 4.1 技术与回归验收

### 4.2 无背景验收（模拟预验收 + 产品负责人最终验收）

**本轮口径（2026-10-21 确认）。** 采用四段式：

1. DSH 实施；
2. DSH 技术/自动视觉自验（由独立验证者执行，不由同一实现者自签）；
3. DSH 模拟无背景预验收（fresh agent，只给 URL、测试账号、任务卡 T1–T8）；
4. 产品负责人（你）最终验收。

模拟预验收不是正式人类无背景验收；它的作用是提前暴露入口、空值、审核、气泡和视觉问题。正式签字只由产品负责人完成。

**目的。** 验证没有 EduFlow / LangGraph / 工作流背景、未读内部文档、未接受操作提示的用户，能独立完成本轮核心任务，并能用自己的话解释输入、运行、审核和结果。模拟用户只能作为预验收，不能替代人类签字。

**模拟用户规则。** 使用 fresh agent（无本会话历史），只提供 URL、测试账号和任务卡；不提供计划、源码、评审记录、验收手册或本对话。只通过普通浏览器 UI 操作，不使用开发者工具、API、数据库；不读取仓库文件。若技术上无法限制其读取仓库，或它读取了内部资料，该轮不算有效模拟，必须重开。主试只重复任务卡，不提示点击路径、不解释术语、不代操作；观察者记录操作路径、停顿、回退、提问、错误和原话。

**真实人类可选。** 如果有未参与实施的同事可做 30–60 分钟任务卡，优先用真人替代或补充模拟；没有真人时，本轮接受“模拟预验收 + 产品负责人最终验收”，并在验收记录中写明“无真实无背景人类用户”的残余风险。

**环境。** Local 或 Hosted 测试环境；独立测试账号与测试定义；不消费用户现有等待任务。三场景 A/B/C（或按 P0/P1 范围裁剪）覆盖启动输入、空值、审核、气泡、子图调用。录屏 + 浏览器窗口录制；记录环境、修订、Run/Thread/checkpoint 身份。模拟用户只使用普通 UI。

**任务卡（只写目标，不写步骤）。**

| 编号 | 任务卡 | 主要观察 |
| --- | --- | --- |
| T1 | 用给定的订单号和客户问题启动流程；说明这两个值会被哪个节点使用，是否进入共享状态 | 能否找到启动入口、理解启动输入与消费者 |
| T2 | 在审核/回应里把“允许空文本”的备注留空并提交；再输入后删除；用高级 JSON 查看；对真正必填的订单号留空 | A 方案下三种操作是否一致；真正必填是否仍阻止 |
| T3 | 缺少必填输入时点击运行；取消填写 | 错误是否在字段旁；是否创建 Run |
| T4 | 找到当前待审核任务；说明在批准什么、依据是什么、批准后会发生什么；切换到另一个待回应任务；刷新 | 审核上下文是否足够；身份是否串线 |
| T5 | 指出启动输入、共享状态、节点读取/写入、人工回应分别在哪里 | 是否仍把四类输入混为一谈 |
| T6 | 不打开原始 JSON，说出消息正文/工具结果/评审结论；再展开详情 | 气泡摘要是否可读；完整结构是否可查 |
| T7 | 同一子图被调用多次时，选择第 2/3 次调用，查看对应输入、步骤和输出；返回主图 | 调用实例是否可区分；选择是否串线 |
| T8 | 如适用：从实训进入工作流，确认输入只读、来源是调用方 | Assignment/API 输入是否被误认为可手改 |

**失败循环（本轮强制）。**

- 第 3 段任一项失败：保留录屏、截图、原话和 Run/身份；记录根因、影响范围和修复方案。
- 修复后先重跑受影响的技术/视觉门，再用**新的 fresh 模拟用户会话**重跑失败任务；不能复用已被提示或已“学会”的会话。
- 循环直到 P0 必须项 T1–T5、P1 项 T6–T7、T8（如适用）全部通过，且无阻塞视觉问题。
- 每轮保留失败与通过证据；不得删除失败记录，不得用“培训后会用”改判。
- 同一问题连续 3 轮无进展时，升级为阻塞并报告，不把失败改判成功；需要改冻结决策时先暂停确认。
- 第 4 段（你的最终验收）发现问题时，同样回到修复→技术/视觉→第 3 段→第 4 段，直到你签字。
- 不设固定轮次上限；每轮新增的修复、证据和残余风险都写入验收记录。

**通过门槛。**

- **预验收 P0 必须**：T1–T5 全部完成，无提示、无代操作；T2/T3 不产生错误 Run；T4 不串线；用户能用自己的话正确解释四类输入和审核依据。
- **预验收 P1 必须**：T6–T7 完成；T8 如适用。
- **最终验收**：你按同一套 T1–T8 与 4.3 视觉清单复核并签字；模拟通过不能替代你的签字。
- 关键任务不允许“主试解释后重试”算通过；发生提示即记录为失败，修复后用**新的 fresh 会话**重测。
- 量表：每个任务后 1–5 分记录“我知道下一步做什么”“我看懂了结果”；P0 任务均值 ≥4，且无单项 ≤2；同时保留开放原话。
- **零阻塞**：没有“必须问开发”的时刻；没有因错误文案、空面板、身份串线或无法返回而放弃。
- **视觉异常即失败**：任务执行中出现浮层遮挡主操作、内容裁切、重复表单、错误层级、任务上下文残影或明显布局跳动，记录为失败，不能以“功能可用”改判。
- **失败处理**：保留失败证据，不以“培训后会用”改判；修复后重测，不能由实施者口头判定通过。

**证据与签署。** 第 3 段报告标注“模拟预验收”，按 iteration 记录每轮任务、卡点、原话、截图/录屏、Run/Thread/checkpoint 身份、环境与修订；第 4 段由产品负责人签署。模拟用户、独立验证角色不能签“正式无背景验收通过”。证据目录建议 `artifacts/workflow/acceptance/input-ux-<date>/`；不得写入凭据、其他用户数据或完整 State。

**残余风险。** 本轮没有真实无背景人类用户；模拟用户可能比真人更耐心、更懂界面，可能漏掉真实用户的困惑。若项目要求正式人类无背景证据，必须补 1 名真实参与者；否则在验收记录中明确接受该风险。

**边界。** 不替代技术验收、API/权限/幂等/检查点证据；不测试性能、容量、多日稳定性或 Hosted 高可用；不要求真实手机或完整键盘无障碍（归 P2 布局专项）。任务卡不包含内部术语；界面必须出现的术语应有就地解释，验收看用户能否理解，而不是要求用户先学术语。

### 4.3 前端完整性与视觉验收

**目的。** 验证本轮变更面在真实浏览器中没有遮挡、裁切、错位、重复表单、错误层级、上下文残影或明显布局跳动；功能正确不等于视觉完整，不能用“点得动”代替“看得清、不会误操作”。

**范围。** Start 输入区、运行准备对话框、运行 tab、人工审核卡与回应表单、执行气泡、子图调用历史、错误/提示条、历史只读启动摘要。既有 P2 布局问题（右侧面板遮挡、390 宽、完整键盘无障碍）不因本轮改动而恶化，但不作为本轮修复目标。

> 说明：右侧面板遮挡指 inspector/panel 是绝对定位覆盖层，画布不会为它让出布局空间；当节点位于面板矩形下方（右侧边缘、宽面板、较大图）时会被盖住，需要关闭面板或平移/缩放画布才能操作。当前小图、节点居中时不一定触发，不能用一张未遮挡截图否定该条件性问题。复现方式：把节点拖到右侧面板下方，或打开宽面板/较大图后选中右侧节点。

**视口与浏览器矩阵。**

- **阻塞**：1280×800、1440×900、1920×1080，Chrome/Chromium 最新稳定版；1440×900 另测 125% 浏览器缩放。
- **记录但不阻塞**：1024×768、390×844（浏览器视口，不等于真实手机）；若变更面在这些尺寸阻断操作，升级为阻塞。
- **冒烟**：Safari、Firefox 至少各做一次变更面检查；资源不足时明确记录未覆盖范围，不能声称全浏览器通过。

**检查项。**

1. **遮挡**：对话框、抽屉、面板、审核卡、气泡不覆盖主操作（运行、提交、关闭、返回）或当前任务的关键依据；不把选中节点遮到无法操作；必要时可平移/缩放画布恢复。
2. **裁切与滚动**：长字段名、长错误、长审核依据、长气泡在容器内滚动；无横向页面滚动、无双滚动条、无被容器裁掉的按钮或标签。
3. **层级**：对话框 > 抽屉/面板 > 气泡/提示 > 画布；toast/error 不盖住提交按钮；多个提示不无限堆叠；关闭后无残留遮罩。
4. **焦点与键盘基础**：对话框有焦点陷阱，ESC/关闭按钮可用，关闭后焦点回到触发按钮；Tab 可达主要控件；鼠标路径完整（完整键盘无障碍归 P2）。
5. **状态一致性**：同一屏不出现两个“启动输入”编辑入口；运行 tab 不再有常驻启动表单；切换运行/历史/子图/待回应任务时，标题、上下文与提交目标同步；无旧任务残影、无“运行中/已完成”矛盾状态。
6. **布局稳定**：打开/关闭面板、切换 tab、选择任务、展开气泡详情不触发画布 ELK/force 重排、fitView 或视口跳变；不出现内容跳动导致的误点击。
7. **文案与视觉层级**：四类输入标签固定且不混用；错误显示在字段旁；空状态有说明；按钮主次清晰；不出现未解释的内部术语（LangGraph、inputBindings、namespace 等）。
8. **控制台与资源**：无新增 console error、未处理 promise rejection、缺失图片/样式/字体；生产构建复验，排除仅 dev/HMR 正常、生产样式顺序不同导致的布局差异。

**证据。** 每个变更面 × 视口的截图（命名含 surface/viewport/revision）、操作序列或录屏、控制台日志、DOM 检查记录、问题清单（严重级别、复现步骤、截图）。至少保留修改前/修改后各一组关键截图；无截图不能签“视觉通过”。

**通过门槛。**

- **阻塞项 0 个**：遮挡、裁切、重复表单、错误层级、上下文串线、阻断主操作、新增 console error。
- 变更面在 1280/1440/1920 全部通过；1024/390 的新变更面不得比修改前更差。
- P1/P2 视觉问题必须有清单、归属和“本轮修复 / 后续任务”的明确结论，不能静默忽略。
- 生产构建至少复验一次；不能用仅 dev/HMR 的结果签收。

**边界。** 既有 P2 布局问题（右侧面板遮挡、390 宽、完整键盘无障碍）保留在 P2，不宣告为已修复（2026-10-21 已确认右侧面板遮挡走方案 A）；本轮只保证变更面不新增遮挡/混乱；不新增重型 E2E/视觉回归框架，优先复用现有浏览器与截图流程；若引入 Playwright 或视觉对比工具，按依赖与维护成本单独评估，不作为本轮默认。

## 10. 当前 DSH 实施与验收适配评估

> 评估日期：2026-10-21。结论不改变第 8 节冻结决策，也不启动实施。

**一句话结论：DSH 支持“完整实施 + 技术/自动视觉验收”，不支持“由 DSH 单独完成全部验收并签字”。**

### 10.1 结论

- **支持**：代码修改、单元/组件/集成测试、类型检查、lint、生产构建、Worker 测试、Local 技术验收、Supabase/Vercel 只读检查与受控操作、Git、证据整理、连接 Playwright 后的截图/DOM/视口检查。
- **不能单独完成**：真实无背景普通用户验收、产品负责人签字、对“混乱/遮挡”的最终人工视觉判断。DSH 可以准备环境、任务卡、录屏和证据，但不能替代人类参与者或签字人。
- **本轮采用（2026-10-21 确认）**：DSH 实施 → 技术/自动视觉自验 → fresh agent 模拟无背景预验收 → 产品负责人最终验收；预验收失败则修复并重新用 fresh 会话验证，循环直到通过。模拟预验收不是正式人类无背景验收，正式签字只由产品负责人完成。

### 10.2 当前能力与限制

| 项目 | 当前状态 | 对计划的影响 |
| --- | --- | --- |
| 代码/测试/构建 | Node 22.22.0、pnpm 9.15.0、Docker 28.4.0、uv 0.12.9；`pnpm test`、`typecheck`、`lint`、`build`、`test:workflow` 可用 | 技术实施与回归可执行 |
| Local Supabase | Docker 可用；`supabase` CLI 不在 PATH，但 `supabase/config.toml` 存在 | Local DB 验收前需安装 CLI 或用 `pnpm dlx supabase`，属于一次性环境准备 |
| Supabase | MCP 已连接 | 可核对项目/迁移/数据；生产写需审批，禁止 reset |
| GitHub | MCP 已连接 | 可查代码、提交与 PR |
| Vercel | MCP 已授权，注册 237 个工具 | 可查部署、日志、环境、DNS、Function 数；生产变更需确认 |
| 浏览器自动化 | Playwright 连接器已上架但当前未连接 | 连接后可自动截图/DOM/视口检查；否则视觉验收需人工浏览器 |
| 文件权限 | danger-full-access，审批 ask | 可实施；生产操作仍受审批约束 |
| 人类验收 | DSH 不是人类用户 | 模拟预验收不能替代人类签字；最终验收由产品负责人完成 |
| 多智能体 | Agent Teams/子智能体可用 | 计划推荐单写作者；最多加 1 个独立验证者，不并行改热点文件 |

### 10.3 推荐执行模式

1. **DSH 单实现者顺序推进 P0→P1**：按已冻结阶段推进，不再拆更细；每个阶段门通过后再继续。
2. **独立验证者**：fresh 子智能体只读跑测试、截图与证据整理，不改生产代码；缺陷交回实现者。
3. **模拟无背景预验收**：fresh agent 只给 URL、测试账号、任务卡 T1–T8；浏览器-only，不读仓库；失败则修复→技术/视觉→新的 fresh 会话重测，循环直到通过。
4. **产品负责人最终验收**：你按 T1–T8 与 4.3 清单复核签字；发现问题回到第 3 段循环。
5. **Hosted 验收**：DSH 用 Vercel/Supabase MCP 做只读与受控检查；生产变更由人类确认并签字。
6. **不得由 DSH 同时担任实现者和最终验收签字人**。

### 10.4 可行性风险

- 8.1 的工程事实（审核上下文字段、子图调用身份、20 Run 快照、Hosted 环境）未核实前，不能承诺“完整实施一定全部通过”；不足时按计划出差距报告，不擅自迁移。
- 视觉验收依赖 Playwright 连接或人工浏览器；未连接时 DSH 只能做代码/DOM 级检查，不能替代真实截图。
- 模拟用户不是人类，可能比真人更耐心、更懂界面，漏掉真实用户的困惑；残余风险必须写入验收记录。若要求正式人类无背景证据，补 1 名真实参与者。
- 失败循环不设固定轮次，可能拉长工期；每轮修复、证据和残余风险都必须记录，不能用“培训后会用”改判。
- 14–20 人日不是单轮工作量；应利用 DSH 的 goal/阶段门跨轮次推进，不能一次性无检查点跑完。
