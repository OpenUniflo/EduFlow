# 三套完整智能体工作流：操作与观察手册

日期：2026-10-20。本文面向本地演示；三套均已通过普通认证 API 保存到当前 Local Supabase，属于 `local-student@eduflow.local`。它们复用现有前端与执行器，没有新增页面、运行时或数据库 schema。

后续人工演示发现的输入/State 可理解性、气泡、审核上下文、子图工作区和可留空字段问题，见 [2026-10-20 用户体验问题记录](WORKFLOW_USER_REVIEW_2026-10-20.md)。这些问题已记录，尚未修复；下文既有 API 自测不代表这些体验项已经通过。

## 工作流究竟存在哪里

**前端工作流库中已经保存的流程，以数据库为准。** 页面通过 `/api/workflows` 读取，服务端按当前登录用户查询；不是每次从代码文件拼出用户流程。当前本地页面连接 Local Supabase，与 Hosted 数据库分开。

| 内容 | 保存位置 | 作用 |
| --- | --- | --- |
| 用户的工作流身份、当前版本和归档状态 | `public.workflow_v2_definitions` | 工作流库条目及版本入口 |
| 每个已保存定义、版本和布局快照 | `public.workflow_revisions` | 固定执行版本、历史只读查看 |
| 当前画布布局 | `public.workflow_editor_documents` | 节点位置、连线等编辑表现 |
| Run、步骤和事件 | `public.workflow_live_runs`、`workflow_run_steps`、`workflow_run_events` | 实际执行结果、过程与故障追踪 |
| 持续会话 | `public.workflow_execution_threads` | 同会话下一轮、等待与恢复身份 |
| 官方图检查点 | `workflow_checkpoints` schema | LangGraph 执行状态和子图 namespace |
| 长期记忆 | `workflow_memory` schema | 跨 Thread 的授权持久记忆 |
| 可复用数据库模板 | `public.workflow_templates` | 模板来源，实例化后成为用户流程 |
| 本次三套示例的可复现定义与布局 | [仓库场景文件](../../src/demo/workflow/scenarios) | 显式演示 seed，不是生产读取 fallback |
| 少量“起步流程”配置 | `src/features/workflow/domain/v2/authoringExamples.ts` 等 | 编辑器中构造初稿；其中前端预览示例需与真实执行区分 |

你在界面保存流程后，数据库会产生新修订；仓库 JSON 不会自动被反向改写。反过来，改仓库 JSON 也不会自动覆盖数据库里你编辑过的流程。创建脚本只补充新示例，不强行覆盖已有条目。导出的配置是定义与布局材料，不是独立可执行部署包。

源码依据：[API 的版本读取与保存](../../api/_lib/workflowV2.ts)、[前端 API Repository](../../src/features/workflow/repository/v2/WorkflowApiV2.ts)。

## 开始前统一操作

1. 打开 [EduFlow](http://127.0.0.1:5173)，登录 `local-student@eduflow.local`。密码见 [本机私有账号页](../../.acceptance/manual-demo-20261020/accounts.private.md)。教师、管理员不自动拥有这些私有流程。
2. 从下表直接进入，或在 **画布** 工作流库搜索“场景 A”“场景 B”“场景 C”。页面已打开但列表没刷新时重新进入工作流库。
3. 顶部选择 **真实执行**，运行环境 **Local acceptance**。不要选“前端预览”或“P5 本地受控流式验收”。
4. 点 **执行**，在 **本次运行输入 → 高级 JSON** 粘贴对应输入，点 **校验 → 运行**。输入是本次调用数据，不随工作流定义保存。
5. 运行完成后点 **返回流程编辑**。下一次顶部运行若弹出“新建一次运行”，核对输入再点 **确认新建运行**。
6. 想修改节点先复制流程，在副本保存、校验和运行；无需修改代码仓。不要重置数据库或重新 bootstrap 账号。

等待表单中的布尔字段是 **“请选择 / 是 / 否”下拉框**，必须明确选择，不是默认不勾选就等于“否”。文字字段如要提交空字符串，最稳妥是在该等待表单的 **高级 JSON** 中明确写 `"字段名":""`；没有填写的字段和空字符串不是同一回事。

| 场景与入口 | 业务闭环 | 模型调用 |
| --- | --- | --- |
| [A · 订单客服与人工审批](http://127.0.0.1:5173/workflows/339fb0e0-bdc2-486f-8210-de48d90971fd) | 客户诉求 → 模型选工具查单 → 建议 → 人工决定 → MCP 演示回执/转人工 | 正常一次查单对应两次模型请求；异常循环受工具/图预算限制 |
| [B · 并行方案评审与逐项确认](http://127.0.0.1:5173/workflows/2db88da0-51bd-4307-b392-c7eb9ace67f3) | 项目说明 → 多维度智能体并行评审 → 每项人工确认 → 汇总报告 | 每个维度一次，输入支持 1–3 个不同维度 |
| [C · 项目跟进与跨会话记忆](http://127.0.0.1:5173/workflows/20488f8d-9b4c-4d17-a384-7adaedf87b21) | 读已确认历史 → 整理本轮进展 → 人工定稿 → 按版本保存 → 下一轮/新会话读取 | 每轮一次；单纯查看历史、回应确认不重新调用模型 |

这些是工作流实验中的业务处理智能体，不是 Learn 模式聊天入口，不替代 Global Assistant，也不读写课程、Assignment、学习进度或 mastery。所有模型结果都是待审核建议。

## 场景 A：订单客服与人工审批

适合展示客服查询、售后建议、人工授权以及“模型决定工具 → 工具结果 → 模型继续”的完整闭环。

### 输入并运行

```json
{
  "orderId": "A1001",
  "question": "请核对订单状态，并建议我下一步如何处理，不要替我执行退款。"
}
```

1. 运行后观察 **客服智能体：决定工具或回复**。第一次应产生结构化工具调用，而不是直接编造订单。
2. 查看 **执行模型选择的订单查询**：工具为 `order_lookup`，参数中应是 `orderId: A1001`，返回本地测试订单事实。
3. 模型根据工具结果再次生成建议。在 **提取完整客服建议** 的输出或 State 中查看 `draft`。
4. 停在 **请审核客服建议** 时，确认内容合理，在 **同意生成演示回执？** 选择 **是**，点 **提交回应并继续**。
5. 查看 **通过 MCP 生成演示回执**，最后看 `status`、`receipt` 和 `draft`。

### 重点看哪里

| 观察位置 | 具体内容 | 通过标准 |
| --- | --- | --- |
| 客服模型节点的执行详情/执行次数 | 第一次工具调用、第二次最终文字；对应输入和 toolCalls | 工具名和参数明确，得到工具结果后继续；不是仅一句“我查过了” |
| 工具调用批次及事件轨迹 | `order_lookup` 的参数、结果、状态 | A1001 来自实际 HTTP 测试服务；模型建议能对上返回事实 |
| State / 提取完整客服建议 | `messages`、`pendingCalls`、`draft` | 消息包含真实 assistant/tool 往返；最终无未消费工具调用 |
| 等待气泡 | 人工布尔确认 | 未确认前不生成 MCP 回执；刷新后仍能找到该任务 |
| 最终输出 | 已确认状态和 Echo 回执 | 回执实际来自 MCP；建议没有被当成已退款/已发货等业务操作 |

本次测试订单 A1001 返回“已发货”，明细 BOOK-1 两件、SHIP-1 一件，合计 128 元。演示时仍以工具当次返回为准；模型文本不要求字句相同。不要把模型描述当订单事实权威。

### 再覆盖一个分支

新开一轮，在 **同意生成演示回执？** 选择 **否** 并提交：应走 **转人工处理，不生成回执**，最终 `status=未批准，需人工处理`。新的模型轮会产生费用；不需要为了查看拒绝逻辑重复运行很多次。

本场景没有真实退款、发邮件或创建客服工单。HTTP 是本地受控订单服务，MCP echo 是真实协议调用的演示回执，不能宣传为已接入企业售后写系统。换未知订单号可能明确失败；不得凭空补一份订单。

**对应架构**：P3 条件路由/循环/人工中断；P4 工具目录及授权；P5 模型流和消息历史；P6 实际 HTTP/MCP 链路与终止保护。LangGraph 负责 StateGraph、条件边、消息 Reducer、interrupt/checkpoint；官方模型 SDK 负责 tool-call 协议，EduFlow 负责工具授权、参数校验、凭据与预算。人工批准不是模型自己给自己授权。

## 场景 B：并行方案评审与逐项确认

适合展示同一任务拆分成多个智能体、独立子图、并行等待、部分回应、批量回应和结果归并。

### 输入并运行

```json
{
  "brief": "两人团队希望两周内上线一个社团活动报名小工具，预算3000元，先支持报名和名单导出。",
  "dimensions": ["成本", "风险", "执行计划"]
}
```

1. 运行后看 **按输入生成评审任务** 输出的 `items`，应有三个维度。
2. **并行分发各维度评审** 通过 Send 创建三个 **独立评审与人工确认子图** 实例。
3. 点击子图 **进入子图查看**；在 **生成本维度评审意见** 的 **执行次数** 中切换，查看输入任务、实际模型输出。相同节点名对应不同 task，并不是同一结论重试三次。
4. 模型生成完成后有三个 **请审核这一项评审意见** 等待任务。用 **选择待回应任务** 切换；若在主图，只需点子图等待气泡的 **进入回应：…**。
5. 先只选择一项，在 **是否采用本项建议？** 选 **是**，备注填“这一项先通过”，点 **提交回应并继续**。
6. 刷新，确认另外两项还在等待，已提交项没有重新提问。继续分别填写；一项选 **是**、备注“采用”，一项选 **否**、备注“后续调整”。可切换任务填完后点 **提交全部已填写回应并继续**，也可以逐项提交。
7. 返回主图，查看 **等待全部评审完成**、**汇总意见与人工决定**，最后读取 `results` 和 `report`。

### 重点看哪里

| 观察位置 | 具体内容 | 通过标准 |
| --- | --- | --- |
| Send 节点 / State.items | 数量和维度 | 三个输入维度对应三个真实任务；不依赖写死的成本/风险身份 |
| 子图模型执行详情 | 每项输入的维度、task、graphPath/namespace、输出 | 三项能准确对应，不串结果；并行完成顺序不固定 |
| 等待任务选择器 | 三项 → 回应一项 → 剩两项 | 部分回应不会误消费其他任务，也不会丢失待办 |
| 子图提取结论气泡 | 当前任务的 `draft` | 审核前能看到自己正在确认的那条建议；切换 task 后重新核对 |
| 汇总节点与最终输出 | 三个 result 的 dimension、draft、accepted、comment | 每个维度恰好一项；两项采用、一项不采用；报告保留人工决定和备注 |

“不采用”表示这一项评审已完成、决定为不采用，所以整图仍可完成。它不是任务执行失败。任何一项尚未回应，最终报告都不能提前显示完整成功。批量提交按钮在未全部填写时禁用是正确行为。

### 用同一套流程换场景

保留结构，只改输入即可，例如：

| 业务 | brief 示例 | dimensions 示例 |
| --- | --- | --- |
| 活动筹备 | 50 人线下分享会，场地预算 2000 元，下周六举行 | `["场地与物资","现场风险","宣传与报名"]` |
| 产品上线 | 小程序新增报名功能，现有用户 300 人，本周只做灰度 | `["用户体验","数据与隐私","上线计划"]` |
| 文案评审 | 一封产品更新通知，目标让老用户理解新增功能，不承诺效果 | `["信息准确性","表达清晰度","行动指引"]` |

维度最多三个且不重复，是当前示例的明确输入范围。输入只是一段用户提供的项目说明，不是经系统验证的业务实体。建议需要现场审核，不能因三个模型都给出文字就认为方案一定正确。

**对应架构**：P3 Send、per-invocation 子图、多节点 interrupt/resume；P4 隔离函数与 Reducer；P5 子图任务归属、历史；P6 并行实模集成。LangGraph 负责 Send 动态调度、task namespace、检查点及合并；EduFlow 负责表单、部分/批量回应、预算与画布定位。三个评审使用同一模型的独立任务，不是三个独立供应商或三个账户。

## 场景 C：项目跟进与跨会话记忆

适合展示短期 State、同 Thread 下一轮、跨 Thread Store、人工定稿、版本冲突保护的区别。

### 第一轮：保存一份明确记录

```json
{
  "projectKey": "demo_project_a",
  "update": "活动报名工具已完成需求访谈；目前还没有开始编码，下周先确认数据字段和报名流程。"
}
```

1. 首次使用此键时，**读取本项目已确认记录** 应返回 `found=false`、`value=null`、版本 0。如果之前演示过，读到旧值是正常的；想全新演示请换一个从未使用的键。
2. 看 **结合历史与本轮输入组织任务** 的输入，区分 `previous` 和 `update`；看模型生成的 `draft`，确认没有编造已完成编码。
3. 等待 **确认后才保存项目记忆**。在 **保存为本项目的长期记忆？** 选 **是**；在 **最终记录（留空采用模型草稿）** 填：`需求访谈已完成，尚未编码；下一步确认报名字段。`，提交。如果要采用模型草稿，在该等待表单的高级 JSON 填 `{"approved":true,"finalNote":""}`。
4. 检查 **构造人工确认后的项目记录 → 按版本保存已确认的记录**，最后 `status=已确认并保存项目记忆`，`record.confirmedNote` 是刚确认的文字。

### 第二轮：同会话继续，但拒绝保存

1. 不点击顶部新运行。打开 **会话与历史操作**，选第一轮会话。
2. 在 **下一轮输入** 填相同 projectKey，update 填：`报名字段已确认，仍未编码；请结合上轮记录给出下一步建议。`
3. 点 **使用当前运行输入继续下一轮**。核对 Thread 不变、Run 变化，读取的 `previous.confirmedNote` 是第一轮已确认记录。
4. 这次在人工确认处选择 **否**；为明确提交空的最终记录，在该等待表单的 **高级 JSON** 填 `{"approved":false,"finalNote":""}`，点 **提交回应并继续**。
5. 最终应为 `未批准，长期记忆未修改`。模型这轮的建议属于草稿，不能自动变成 Store 权威记录。

### 第三轮：新会话还能读到第一轮记录

返回流程编辑，用顶部 **运行** 开新 Thread，输入相同 projectKey 和“新会话，请读取本项目已确认历史”。

**通过标准**：新 Thread 仍读到第一轮确认记录，版本没有因为第二轮拒绝而增加；不能读到第二轮未经批准的草稿。可在这一轮也选择不保存以结束运行。

### 重点看哪里

| 观察位置 | 具体内容 | 通过标准 |
| --- | --- | --- |
| 读取记忆节点的输出 | found/value/version | 真实服务器读取，不是上次页面残留 |
| State.previous 与模型输入 | 已确认历史和本轮输入分别存在 | 模型有历史依据，不能把用户草稿当已确认事实 |
| 人工确认气泡 | approved、finalNote | 可用人工文字替代模型草稿；未批准不写 Store |
| 保存节点详情 | key/value/expectedVersion | 使用先读到的版本做 CAS；冲突明确失败，不覆盖别人刚保存的数据 |
| 会话与历史操作 | Thread/Run/轮次 | 下一轮同 Thread；顶部运行新 Thread |
| 长期记忆面板 | 范围“此工作流私有”、集合 `projects`、键 `demo_project_a` | 刷新、新会话仍可读；每个项目键独立，其他账号不可读 |

记忆面板默认集合为 `default`，这里必须改成 **projects** 再点 **读取记忆列表**。当前示例 TTL 为 1440 分钟；过期后不保证保留。项目键只用英文字母、数字、下划线或连字符，长度 1–80；例如 `demo_project_b`。切换键可演示不同项目，不需要复制整个工作流。

`previous` 是进入本轮时读到的旧值；最终 `record` 是本轮准备保存的确认对象；`savedVersion` 在拒绝轮可能保留同会话前轮值，**不能仅看这个字段就认定发生了写入**。以分支、保存节点是否执行和 Store 当次读取版本判断。`record.rounds` 是此键已确认保存的次数，不等于 Thread 的执行轮数。

**对应架构**：P5 官方 AsyncPostgresStore、持续 Thread、历史检查点；P6 记忆提交的事务/权限一致性。LangGraph 提供持久化图与 Store；EduFlow 增加 owner/env/workflow 命名空间、TTL/CAS、确认门槛和预算。历史分支不会自动回滚 Store，重新保存仍需校验当下版本。

## 演示时建议固定看的五个位置

1. **执行 → 本次运行输入**：确认自己实际提交了什么。
2. **节点气泡与执行详情**：按“读取 → 处理 → 写入”解释；多次执行要切换执行次数，不能只看同名节点。
3. **执行步骤/事件轨迹**：工具名、task、尝试次数、实际调用结果；需要时查看原始数据，不以连线代替执行证据。
4. **State 与最终输出**：State 是中间工作区，最终输出由显式绑定得到；生成中的片段不等于提交成功。
5. **运行历史/会话与历史操作**：区别新运行、等待恢复、下一轮与历史分支；展开 **当前运行与检查点身份** 核对 Thread/Run/Checkpoint。
