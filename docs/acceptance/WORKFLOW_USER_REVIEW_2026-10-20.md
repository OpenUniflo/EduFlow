## WF-UX-01：运行输入与 State 的关系

用户问题：场景 A 的运行输入是哪个节点需要的？是否每个节点应对应 State 中一个字段？

### 当前实际关系

场景 A 顶层 `inputSchema` 定义 `orderId`（订单号）、`question`（客户诉求）。开始运行前，系统先按这个流程级输入契约校验；**第一个函数节点 `prepare`，即“组织客服任务与工具约束”，直接读取这两个 Input 字段**，构造模型消息并写入 State 的 `messages` 等字段。开始节点本身没有配置读取这两个字段。

| 层次 | 场景 A 当前内容 | 含义 |
| --- | --- | --- |
| 本次 Run Input | `orderId`、`question` | 本次调用参数，通过节点的 `source: input` 绑定读取 |
| `prepare` 节点读取 | `/orderId`、`/question` | 把本次输入组织成任务与工具约束 |
| 共享 State | `messages`、`pendingCalls`、`draft`、`approved`、`status`、`receipt` | 图运行中的共享工作状态；后续节点按绑定读写 |
| 人工回应 | `approved` | 到人工节点时补充，再由 `resumeWrites` 映射到 State |

**节点与 State 字段不是一对一。** 一个节点可读取/写入多个字段；同一字段可被多个节点读写；某些控制节点不写业务字段。节点也可直接读取 Input，而不必先把所有 Input 复制到 State。是否需要把某个输入长期保留到 State，应由实际消费者决定。

这里需要记录的体验缺口是：页面只显示运行表单，没有清楚说明“谁声明、谁消费、之后写到哪里”，用户必须点配置或看代码才知道。用户关于“状态字段与节点”的疑问，不能通过强行建立一节点一字段的新规则解决。

截图：[20:47:04，场景 A 运行输入](assets/workflow-user-review-20261020/01-scenario-a-input.png)。图中订单号/客户诉求为空，二者当前均有 `minLength: 1`，提示非空是符合现有契约的；这张图本身不证明“可留空字段被错误拒绝”。

来源：[场景 A 定义](../../src/demo/workflow/scenarios/order-service.json)、[创建脚本](../../scripts/workflow/examples/create-agent-scenarios.mjs:37)。本次另以普通认证 GET 核对数据库当前定义，仍为 revision 1，与上述输入及绑定一致。

### 未来验收意图，尚未实施

从运行表单即可找到对应消费节点和读写字段；从节点也可反查所需输入及来源。Input、共享 State、节点返回和人工回应保持区别，不重复制造权威数据。

## WF-UX-02：执行气泡难读

用户观察：气泡中的 JSON 很长，不能直观看出具体含义。

源码现状：`summaryFields` 只取对象前两个字段；`briefValue` 将复杂对象 `JSON.stringify` 后截为约 110 字符；气泡默认取该节点最近一条步骤。函数/子图的处理描述常退化为“执行节点处理”。因此消息对象优先露出 id/role 等结构，评审数组优先露出 JSON 外壳，正文与业务含义容易被截掉。

这并不是没有记录输入输出，而是摘要方式不足以支持用户理解。右侧已有更详细的节点执行记录，也不能抵消气泡本身难读的问题。

## WF-UX-03：人工介入缺少判断上下文

用户要求：在人工介入节点提取上下文中的必要信息，辅助人工判断。

当前 `NodeResponseForm` 接收的是标题、回应 Schema、回应值与提交回调，没有承载“待审核对象、必要事实、关联输出”等上下文展示参数；等待气泡主体直接是这份表单。其他节点已经有信息，并不意味着审核人能在当前审核入口看清它们。

| 场景 | 审核入口至少需要看清的内容 |
| --- | --- |
| A 订单客服 | 对应订单/客户诉求、实际查单结果、待审核建议、批准后将执行什么 |
| B 并行评审 | 当前是哪一个维度/调用、该项结论、项目约束、回应会影响哪一项 |
| C 项目记忆 | 历史已确认记录、本轮进展、待保存草稿/最终稿、批准后写入的项目范围 |

这是待完善的产品需求，不表示把整个 State 或原始内部信息全部摊给用户。展示应基于本次实际执行的授权数据，并与当前 task/namespace 对齐；不能混入其他并行任务、其他历史或未确认内容。

审核人无需离开当前审核入口翻长 JSON 即可作出判断；切换不同待回应任务时，展示内容与提交对象同步切换，刷新后身份不串线。

## WF-SUB-01：子图工作区、调用历史与可复用工作流

用户期望完整记录如下：

1. 进入子图后，是与主流程同类的完整工作流画布工作区，可以直接返回场景 B 主流程。
2. 子图有清楚的每次调用记录，可以选择、查看每次调用的输入、结果、步骤、等待与状态，而不只显示同名节点的最近一次数据。
3. 子图本身可以独立新建、直接打开编辑、单独使用，也可以被主流程作为子图引用和复用。

### 当前实现与缺口

| 当前已有 | 当前尚不能视为满足 |
| --- | --- |
| `core.subgraph.config.graph` 内嵌一份完整图定义 | 不代表它已作为拥有独立持久身份的工作流资产注册 |
| 按 graphPath 切换子图 Definition/布局，面包屑返回主图 | 仍复用根 Controller；保存、运行、撤销归属整份父文档 |
| 步骤有 graphPath、taskId、namespace，历史面板可读部分子图范围检查点 | 不代表已提供按子图调用实例组织的完整历史浏览器 |
| 节点详情有“执行次数”下拉，能查看当前已加载步骤中的多次执行 | 不等于子图级的“选择本次调用，查看整张图对应结果”，也未覆盖跨父 Run/继续执行记录的完整串联 |
| 官方 SDK 支持嵌套执行与检查点 | 不自动提供可复用子工作流的产品身份、路由、版本管理和历史 UI |

关键原因：`scopedWorkflow` 只替换当前 Definition/Editor 投影，其余运行与历史仍复用根对象；`visibleSteps` 按 **graphPath** 过滤，这个路径能区别“哪个子图节点”，但同一个节点被 Send 调用三次时路径相同，仍需更细的 invocation/task/namespace 区分。气泡按 nodeId 取最近步骤；选择底部根运行历史还会回到主图。

因此，本轮结论是**调用记录组织和工作区能力不足**，不能仅根据页面不可用就认定底层从未持久化或数据全部丢失。已有实例身份和检查点应成为后续诊断依据，不应重新制造另一套执行记录。

来源：[子图作用域投影](../../src/features/workflow/application/v2/scopedWorkflow.ts:4)、[内嵌图读取](../../src/features/workflow/domain/v2/authoring.ts:31)、[路径过滤](../../src/features/workflow/editor/v2/LiveWorkflowEditor.tsx:147)、[最近步骤选择](../../src/features/workflow/editor/v2/executionPresentation.ts:40)、[P5 历史范围](../../src/features/workflow/editor/v2/SessionHistoryWorkspace.tsx)。

### 两部分分别记录，均未实施

- **调用观察能力**：按父 Run/Thread、子图节点、具体调用实例组织历史；选择实例后整张子图的步骤、输入、输出、等待及检查点一致切换。并发三次与串行多次都应可区分。
- **可复用工作流能力**：独立创建/编辑/运行的工作流能够被父图引用。涉及引用身份、版本冻结、输入输出契约、授权、编辑生效范围、调用来源与循环引用约束，需要后续单独细化，不能当作只加一个“返回”按钮。

保留同一个工作流领域和运行边界，不因为称作子图就另建一套平行的工作流系统。本轮只记录用户方向，不把引用/内嵌兼容方案视为已经定案。

## WF-FORM-01：“可留空”但留空报错

### 已确认现象与范围

- B 子图审核：`comment` 标签“人工审核备注（可留空）”，但 `required=[accepted, comment]`。
- C 审核：`finalNote` 标签“最终记录（留空采用模型草稿）”，但 `required=[approved, finalNote]`。
- 两个文本字段都没有 `minLength: 1`，所以**空字符串本身合法**；`null` 不合法。
- 当前 A revision 1 的人工回应只有必填布尔字段 `approved`，没有同类可留空文本；运行输入订单号/客户诉求都明确非空。用户报告 A 也有类似现象继续保留，具体字段尚待定位，不能把截图 1 的必填提示混为同一个原因。

### 原因链

1. 场景创建脚本的 `obj()` 将全部属性自动放进 `required`，没有分别表达“字段可省略”和“字段必须存在但允许空字符串”。
2. 待回应草稿初始为 `{}`。表单的文本框用 `current` 不存在时显示 `""`，但显示为空不等于已经把这个空字符串写入草稿对象。
3. 未编辑该空框，提交对象可能是 `{"approved":true}`。Schema 要求 `finalNote` 存在，因此报必填。
4. 高级 JSON 明确提交 `{"approved":true,"finalNote":""}`，字段存在且类型合法，于是通过。C 的后续逻辑才会把这份显式空字符串解释为“采用模型草稿”。
5. 这不是高级 JSON 免校验；两种编辑方式仍走同一份约束，只是提交值不同。单纯切换到 JSON、不补字段，并不会天然修复错误。

类似地，“先输入一个字符再删掉”在当前文本控件中会触发 onChange，把 `""` 写入对象；“从未输入过”的视觉空白却可能仍是缺失。两种看起来相同的操作得到不同有效载荷，是当前体验不一致的核心。

| C 回应数据 | 校验结果 | 原因 |
| --- | --- | --- |
| `{"approved":true}` | 不通过 | 缺少 required 属性 finalNote |
| `{"approved":true,"finalNote":""}` | 通过 | 存在合法空字符串 |
| `{"approved":false,"finalNote":""}` | 通过 | false 是明确选择，不是缺失 |
| `{"approved":true,"finalNote":null}` | 不通过 | null 不符合 string 类型 |

截图：[21:04:37，C 的空白最终记录报必填](assets/workflow-user-review-20261020/03-scenario-c-blank.png)。源码：[全属性 required 的生成器](../../scripts/workflow/examples/create-agent-scenarios.mjs:21)、[空白控件与事件写值](../../src/features/workflow/editor/v2/SchemaForm.tsx:122)、[空草稿](../../src/features/workflow/editor/v2/LiveWorkflowEditor.tsx:220)、[统一提交校验](../../src/features/workflow/editor/v2/NodeResponseForm.tsx:11)、[服务端回应校验](../../services/workflow/src/eduflow_workflow/interrupts.py:27)。

### 本轮验证与此前验收的限度

已使用前端同版本 Ajv 和相同配置，对当前示例 Schema 做 **10 组离线载荷校验**，结果符合上述区别，见 [校验原始记录](assets/workflow-user-review-20261020/blank-field-probe.json)。这不是新增 UI 提交或真实 API 恢复实验，没有消费用户当前的等待任务。

此前三场景集成脚本显式提供 `comment`/`finalNote`（包括 `""`），所以那 11 项通过证明的是 API 有效载荷路径，**没有覆盖“普通表单未触碰空框”的用户操作**。此前手册里改用高级 JSON 的建议只是绕行，不是问题修复，不能作为这项体验验收通过。

### 未来验收意图，尚未实施

界面“可留空”的语义与提交结果一致；原样留空、输入后删除、表单/JSON 往返的结果一致。必须非空的订单号/客户诉求仍阻止空值；布尔 false、数字 0、合法空列表不能泛化成“没填”。具体采用可省略字段还是显式空值归一化，留待后续方案决定，不能一律给所有字段补默认值或放宽全部校验。

## WF-NAME-01：唯一现役工作流仍带 V2 命名

补充日期：2026-10-21。用户由 `api/_lib/workflowV2.ts` 提出疑问：V2 是什么，为什么同时存在两个版本的 Workflow？状态：**已核对、已记录，待处理；本次不修改实现。**

当前统一入口 [api/workflows.ts](../../api/workflows.ts) 只调用 [workflowV2.ts](../../api/_lib/workflowV2.ts) 的处理器。当前正式实现为同一套 Definition、API 仓储、LangGraph 执行边界和 React Flow 编辑器；旧运行路径已经退役。旧浏览器存储清理、历史保全不代表第二套执行器仍在使用。

问题在于重构时保留的 `workflowV2`、`WorkflowV2Entry`、各层 `v2/` 等源码名称，容易让维护者误认为仍有 V1/V2 两套并行产品，需要额外解释才能确认当前唯一实现。

后续整理边界：

- 可将现役源码文件、目录、组件和内部符号统一为清楚的职责名称，同时更新导入、测试、文档和构建引用，避免保留无消费者的兼容转发文件。
- `schemaVersion: "2.0"` 表示持久数据契约版本，应与源码命名区分；编辑器文档自身的版本号也不代表另一套工作流运行时。
- 数据库表名、RPC、已应用迁移、持久定义和历史记录身份不能通过全局替换一起改名。已应用迁移保持不可变；确有数据层改名需求时须另行制定向前迁移和兼容方案。
- 服务端源码改动可能改变 executorDigest，须检查旧检查点兼容与发布衔接，不能为清理名称而绕过执行器恢复约束。

未来完成门槛：源码入口与目录不再造成双运行时误解；所有调用和文档引用有效，类型检查、相关回归及构建通过；持久数据协议、历史和运行恢复语义保持有效。本条仅登记问题及整理约束，尚未确定具体改名清单或启动开发。
